# Feature Specification: MISA eSign — Webhook Receiver

**Feature Branch**: `004-misa-esign-webhook`
**Created**: 2026-05-22
**Status**: Draft
**Input**: User description: "Add support for receiving asynchronous signing-status notifications from MISA eSign via webhook, as an alternative to polling /Signing/status. MISA POSTs the documented webhook envelope { messageId, clientId, extraData, status, errorCode, transactionId, signatures: [{ documentId, signature }] } to a partner-hosted endpoint when all documents in a transaction are signed successfully. The slice ships: (a) a typed Domain model and Application-layer handler for the webhook envelope; (b) a verification helper that validates clientId and matches messageId / transactionId against in-flight signing sessions; (c) a wired-up minimal-API endpoint in samples/MisaConnect.Samples.Api/ that accepts the webhook, returns the documented { errorCode, devMsg, userMsg } acknowledgement, and finalizes signed documents by calling slice 1's /documents/attachment path. The deliverable extends slice 1's test suites: unit tests using mock fixtures for envelope parsing, transactionId reconciliation, duplicate-delivery handling, and the success/failure acknowledgement shapes; plus integration tests that drive the sample API's webhook endpoint with synthetic MISA-shaped payloads and verify the attached-signature finalization path. Reuses slice 1's signing-session bookkeeping, attach call, and HTTP plumbing. Out of scope: webhook signature / HMAC / replay protection beyond what MISA's doc specifies (none documented), durable webhook queueing, and webhook registration / discovery (registration is handled with MISA out-of-band per the doc). Source doc: docs/misa-api-reference/Tài liệu tích hợp API eSign RemoteSigning - V2.md."

## Clarifications

### Session 2026-05-23

- Q: How does the SDK obtain the `messageId` it uses as the idempotency key? → A: MISA generates `messageId` server-side. The SDK reconciles sessions by `(clientId, transactionId)` and uses the MISA-supplied `messageId` purely as the post-arrival dedupe key. MISA's documented `/Signing/hash` request body has no `messageId` field, so the SDK never sends one.
- Q: What additional HTTP-layer authentication must the sample API's webhook endpoint enforce, on top of the `clientId` body match? → A: A configurable shared-secret URL segment (`/esign/webhook/{secret}` bound from `Misa:ESign:Webhook:Secret`) plus an optional CIDR allowlist (`Misa:ESign:Webhook:AllowedIps`). Both are configurable opt-ins (no default); when neither is configured AND `Webhook.Mode` is `Webhook` or `Both`, the sample logs a startup `WARN` so production misconfiguration is loud. MISA's API doc does not mandate a transport-layer signature header — this is consumer-side defense-in-depth.
- Q: When `/documents/attachment` finalize fails on first webhook delivery, what does the SDK return? → A: Return a failure ACK and do NOT cache it. MISA's next delivery of the same `transactionId` triggers a fresh finalize attempt; the SDK retries as many times as MISA delivers, bounded by `Session.Ttl`. Cache the ACK only on a successful finalize. This is the standard "exactly-once-on-success, at-least-once-on-failure" webhook contract — turns transient finalize blips into recoverable retries instead of stuck transactions.
- Q: What is the default `Session.Ttl`? → A: Fixed default of 24 hours, configurable via `Misa:ESign:Webhook:Session:Ttl`. Decoupled from slice 1's `SignTimeout` (a polling-mode budget measured in seconds, which is unrelated to how long MISA may keep retrying webhook deliveries). Matches the order of magnitude used by comparable webhook platforms (Stripe, GitHub, Twilio) — gives MISA an entire business day to retry transient finalize failures while capping in-memory store growth at one day's signing throughput.

### Session 2026-05-24

- Q: When should the SDK register the `SigningSession` in `ISigningSessionStore` relative to the `/Signing/hash` call? → A: Register **after** `/Signing/hash` returns. The session's primary key is `(clientId, transactionId)` and `transactionId` is MISA-issued in the `/Signing/hash` response, so it does not exist before the call. Early-arrival webhooks (MISA's push racing the SDK's `/Signing/hash` response unwind) surface as `UnknownTransaction` per FR-082; MISA's natural webhook-retry replays the delivery after the session is registered. This matches Assumption 8's "`transactionId` is the canonical work-unit" framing and avoids a two-phase store contract.
- Q: What happens on duplicate envelope-status `FAILED` / `CANCELLED` webhook deliveries for the same `(clientId, transactionId)`? → A: The first terminal-status delivery returns a success ACK to MISA per FR-083 AND invokes the consumer's delivery hook exactly once with the typed `TerminalWithoutFinalize` outcome. The success ACK + the terminal outcome are cached on the session record. Subsequent duplicate deliveries (same `transactionId`, whether the same or a fresh `messageId`) short-circuit to the cached success ACK; the consumer's delivery hook is NOT re-invoked. This extends FR-080's "exactly-once delivery to the consumer per `(clientId, messageId)`" guarantee to terminal-status outcomes — the cached envelope is a success ACK so it remains consistent with FR-081's "failure ACKs are NEVER cached".
- Q: How should the sample API surface the `X-Forwarded-For` requirement so consumers behind a reverse proxy don't silently allowlist the proxy's IP? → A: The sample API at `samples/MisaConnect.Samples.Api/` MUST ship a commented-out `ForwardedHeadersOptions` example snippet (with TODOs pointing the consumer to set `KnownProxies` / `KnownNetworks` for their environment) AND a security-note paragraph in `samples/MisaConnect.Samples.Api/README.md` (or the slice-4 `quickstart.md`) explaining that without it, `Webhook.AllowedIps` matches against the proxy's IP, not the real client. The SDK takes no ASP.NET dependency. An additional integration-test row in `WebhookCidrAllowlistTests` MUST exercise a forwarded-headers-wired host and assert the forwarded IP is correctly matched against the configured CIDR ranges. FR-100's contract (consumer configures `ForwardedHeadersOptions`) is unchanged — this clarification covers the sample-API affordance + docs + test coverage.
- Q: How should slice-2's 2FA contract (FR-090) be verified after the slice-4 internal refactor of `SignPdf` / `SignXml` / `SignWord` / `SignExcel`? → A: Add an explicit slice-4 unit test asserting a 2FA-enrolled fixture (using slice-2's `StubOtpProvider`) flows through `BeginSignPdfAsync` and invokes `IOtpProvider` per slice-2's contract. The verification gate is captured as a new measurable outcome `SC-038`. This catches any silent regression introduced by the `BeginSign{Format}` factoring (T022–T025) without depending on slice-2's own test suite to discover the failure.

## User Scenarios & Testing *(mandatory)*

This feature is slice 4 of the `MisaConnect.ESign` product family and runs last in the slice plan — after slices 1 (PDF foundational flow), 2 (2FA / OTP), and 3 (multi-format) are merged. It builds directly on slice 1's auth, token caching, refresh-on-401, header handling, certificate selection, transport retry, and the signing pipeline; and on slice 3's per-format `/documents/attachment` shaping. It introduces the **only async-completion alternative** to slice 1's `/Signing/status` polling loop. The actor in each story is a **consumer developer** integrating the SDK into their .NET service so that, instead of holding a request open while polling, the consumer initiates a sign and lets MISA push the completion notification to a partner-hosted webhook endpoint.

### User Story 1 - Initiate a webhook-mode sign and let MISA push completion (Priority: P1)

A consumer developer's service already uses slice 1's blocking PDF facade. The consumer's product now wants to free up the calling thread/request while MISA processes the sign — e.g. an HTTP API that returns `202 Accepted` to its own caller and finalizes the signed PDF when MISA's webhook fires. The consumer invokes a **non-blocking** initiation facade method (e.g. `BeginSignPdfAsync`) that runs the slice 1 pipeline up to `/Signing/hash` and returns a `transactionId` plus the bookkeeping needed to finalize later. The consumer's webhook endpoint receives the MISA-shaped envelope, hands it to the SDK's Application-layer handler, and the SDK reconciles by `(clientId, transactionId)` against the in-flight session (the MISA-supplied `messageId` is then captured on the session for post-arrival dedupe), then calls `/documents/attachment` with the webhook's signature payload to produce the final signed bytes. The handler returns a typed result the consumer's endpoint can dispatch (e.g. into a notifications queue, a database, or a SignalR push) and an ACK envelope `{ errorCode, devMsg, userMsg }` to return to MISA.

**Why this priority**: This is the headline value of the slice. Without it, the SDK only supports synchronous polling — fine for short documents but a poor fit for ASP.NET request handlers, serverless functions with execution caps, or any consumer that prefers a push-based completion. P1 because without it the slice ships no consumer value; P2 and P3 are operational refinements on top of P1.

**Independent Test**: Drive against the in-repo fake server (no MISA needed) end-to-end: (1) invoke the SDK's `BeginSignPdfAsync` with a one-page fixture PDF — assert it returns a `transactionId` and does NOT call `/Signing/status`; (2) POST a synthetic MISA-shaped webhook envelope referencing that `transactionId` and the configured `clientId` into the sample API's webhook endpoint; (3) assert the SDK reconciles the envelope to the session, calls `/documents/attachment`, returns signed PDF bytes to the consumer's endpoint, and emits the documented `{ errorCode, devMsg, userMsg }` success ACK to MISA. Demonstrable end-to-end against the MISA eSign sandbox by registering the sample API's webhook URL with MISA out-of-band and repeating the same exercise with a real signing transaction.

**Acceptance Scenarios**:

1. **Given** valid sandbox credentials, an ACTIVE certificate, and a registered webhook URL on the MISA side, **When** the consumer invokes `BeginSignPdfAsync` with a one-page PDF, **Then** the SDK returns a non-empty `transactionId` and the SDK performs zero `/Signing/status` polling requests for that transaction across the rest of the test.
2. **Given** the SDK has begun a sign and is waiting for MISA's webhook, **When** the sample API's webhook endpoint receives a MISA-shaped envelope referencing the matching `transactionId` and `clientId` with `status = SUCCESS` and a non-empty `signatures[]`, **Then** the endpoint hands the envelope to the SDK's Application-layer handler, the handler reconciles the session by `(clientId, transactionId)` and records the inbound `messageId` for dedupe, calls `/documents/attachment` exactly once, and the endpoint surfaces the signed PDF bytes to the consumer-supplied delivery hook.
3. **Given** the same in-flight session, **When** the webhook endpoint hands the envelope to the SDK handler, **Then** the handler returns an ACK envelope `{ errorCode, devMsg, userMsg }` whose `errorCode` reads "0" (or the equivalent documented success sentinel — see Assumption 6) and whose `devMsg`/`userMsg` are populated per the configured success-ACK template; the endpoint returns that envelope verbatim to MISA.

### User Story 2 - Duplicate webhook delivery is idempotent (Priority: P2)

MISA's documentation does not promise at-most-once delivery, so the consumer's webhook endpoint may receive the same MISA-supplied `messageId` more than once (network retries, MISA-side requeue, etc.). The SDK MUST treat the first valid delivery for a given `(clientId, messageId)` as authoritative — running the `/documents/attachment` finalize exactly once, then caching the finalize result on the session record (looked up by `transactionId`) and indexing the cached result by `messageId` for fast dedupe. Subsequent deliveries with the same `messageId` MUST short-circuit: the SDK returns the same success ACK to MISA but does NOT invoke `/documents/attachment` a second time and does NOT re-deliver signed bytes to the consumer-supplied delivery hook.

**Why this priority**: Without idempotency, a single signing event can finalize twice — wasting an attachment call (rate-limit / cost risk), double-firing the consumer's delivery hook (duplicate downstream side effects in databases, queues, or user notifications), or surfacing inconsistent error ACKs across deliveries. P2 because the P1 happy path technically works on the first delivery without it, but no production team would ship without it.

**Independent Test**: With the in-repo fake server, run the slice 4 happy path once (begin + first webhook → finalized signed bytes). Then POST the **exact same** webhook envelope (same MISA-supplied `messageId` and `transactionId`) to the sample API's endpoint a second and third time. Assert: (a) the `/documents/attachment` request counter on the fake server stays at 1 across all three deliveries; (b) the consumer-supplied delivery hook is invoked exactly once; (c) all three responses to MISA are byte-identical success ACKs. Then drive a separate failure scenario: configure the fake server to return a 5xx on the first `/documents/attachment` call and 200 on the second; POST the same webhook envelope twice and assert: (a) the `/documents/attachment` counter reads 2 (fresh attempt on the second delivery); (b) the consumer's delivery hook is invoked exactly once on the second delivery's success; (c) the first response is a failure ACK and the second is a success ACK.

**Acceptance Scenarios**:

1. **Given** the SDK has finalized a transaction via the first webhook delivery, **When** an identical webhook envelope (same MISA-supplied `messageId`) arrives a second time, **Then** the SDK returns the cached success ACK and performs zero additional `/documents/attachment` calls.
2. **Given** a duplicate webhook delivery for an already-finalized transaction, **When** the SDK processes it, **Then** the consumer-supplied delivery hook is NOT invoked again — the SDK guarantees exactly-once delivery to the consumer per `(clientId, messageId)`.
3. **Given** the first webhook delivery for a `transactionId` triggered a `/documents/attachment` finalize that failed (transport error after retry budget exhausted, or MISA 4xx), **When** MISA delivers a subsequent webhook for the same `transactionId` (whether the same `messageId` or a fresh one), **Then** the SDK runs a fresh finalize attempt; success on any subsequent attempt caches the success ACK and invokes the consumer's delivery hook exactly once. Recovery from transient finalize failures is automatic via MISA's natural retry; failure ACKs are NEVER cached.

### User Story 3 - Webhook envelope validation and typed failure ACKs (Priority: P3)

The SDK's webhook handler validates four things on every inbound envelope before doing any work: (1) the envelope parses against the MISA-documented shape; (2) `clientId` matches the configured `Misa:ESign:ClientId`; (3) `transactionId` matches an in-flight session in the registered `ISigningSessionStore`; (4) when `status = SUCCESS`, `signatures[]` is non-empty AND every entry's `documentId` matches one the session recorded at `/documents/hash` time. Each failure mode produces a distinct typed error that the consumer's webhook endpoint surfaces as the `{ errorCode, devMsg, userMsg }` ACK to MISA. Logging continues to omit signature payloads, `documentBytes`, certificate private material, and end-user PII as required by slice 1's `FR-019` and slice 3's `FR-063`.

**Why this priority**: Operationally important — webhook endpoints are public-internet-reachable by design, and the consumer needs to distinguish "MISA delivered a malformed payload" from "MISA delivered for a transaction this process didn't start" from "the configured `clientId` doesn't match MISA's expectation". Without typed validation errors, the consumer's endpoint either returns `500` for every failure (forces MISA to retry forever) or `200` for every failure (silently drops state). P3 because the P1 happy path works without it on well-formed deliveries, but no production deployment will ship without it.

**Independent Test**: Drive the sample API's webhook endpoint with five rejection fixtures: (a) a body that fails the documented shape (e.g. missing `transactionId`); (b) a body with `clientId = "wrong-client"`; (c) a body with `transactionId` matching no in-flight session; (d) a body with `status = SUCCESS` but `signatures = []`; (e) a body whose `signatures[].documentId` does not match any document recorded by the session. For each: assert the endpoint returns a `{ errorCode, devMsg, userMsg }` envelope with a non-success `errorCode`, the surfaced exception type matches the documented mapping, the captured log output contains no signature payload / no document bytes / no private-key material, and no `/documents/attachment` call is made.

**Acceptance Scenarios**:

1. **Given** a webhook envelope with `clientId` that does not match the configured `Misa:ESign:ClientId`, **When** the SDK handler validates it, **Then** the handler returns a typed `ClientIdMismatch`-class ACK with a non-success `errorCode`; it does NOT call `/documents/attachment` and does NOT invoke the consumer's delivery hook.
2. **Given** a webhook envelope referencing a `transactionId` for which no session is recorded in `ISigningSessionStore` (or whose session has expired per the configured TTL), **When** the SDK handler validates it, **Then** the handler returns a typed `UnknownTransaction`-class ACK; the consumer's endpoint surfaces it to MISA verbatim.
3. **Given** any successful or failed webhook delivery, **When** logs are inspected, **Then** no log line contains: any `signatures[].signature` value, any `documentBytes` value, any certificate private-key material, the `AuthorizationRM` header, or end-user PII. The MISA correlation ID is propagated onto every log line touching this transaction.

### Edge Cases

- **Webhook arrives before the SDK's `BeginSignPdfAsync` call returns** (race between MISA's push and the SDK's `/Signing/hash` response unwinding) → the inbound delivery is treated as `UnknownTransaction` per FR-082 because the session record is registered immediately AFTER `/Signing/hash` returns (the session's primary key requires the MISA-issued `transactionId`; Clarifications Session 2026-05-24). MISA's natural webhook-retry replays the delivery once the session is registered; on a successful replay the SDK proceeds normally. If MISA exhausts its retries before the session lands (extreme network skew + a sample API that returns a `200 OK` on the first `UnknownTransaction` ACK), the consumer's signed bytes are not produced for that transaction and the consumer's downstream observes the missing delivery as a normal MISA-side timeout.
- **`/documents/attachment` finalize fails transiently on first webhook delivery, succeeds on a subsequent delivery** (per US2 acceptance scenario 3) → first delivery returns failure ACK, no cache, no delivery-hook invocation; later delivery runs a fresh finalize attempt and on success caches + invokes the delivery hook exactly once. The consumer never sees the transient failure unless they inspect logs.
- **`/documents/attachment` finalize fails repeatedly until `Session.Ttl` elapses** → session record evicted on next delivery; that delivery surfaces `UnknownTransaction`. The consumer's delivery hook is never invoked for this `transactionId`. Diagnostic data is in the structured logs (per FR-088, every finalize attempt + failure is logged with correlation ID, transactionId, failure category).
- **Webhook delivers `status = FAILED` or `status = CANCELLED`** → SDK does NOT call `/documents/attachment`; it surfaces a typed terminal-state result to the consumer's delivery hook carrying the MISA `errorCode` and the `transactionId`, and returns a documented success ACK to MISA (the webhook was successfully received and processed — MISA's transaction-level failure is a separate concern).
- **Webhook delivers `status = SUCCESS` but `signatures = []`** → SDK surfaces a typed `IncompleteSuccessEnvelope`-class error (per US3 acceptance scenario via FR-082) and returns a non-success ACK; no `/documents/attachment` call is made.
- **Webhook delivers `signatures[].documentId` that does not match any recorded session document** → SDK surfaces a typed `DocumentIdMismatch`-class error and returns a non-success ACK; no `/documents/attachment` call is made.
- **Session expires before the webhook arrives** (MISA late-delivers past the configured `Webhook.Session.Ttl`, default 24h per Assumption 4) → SDK treats it identically to `UnknownTransaction` per FR-082; the session record was already evicted by the in-memory store's TTL.
- **Consumer mixes polling and webhook for the same `transactionId`** — slice 4 expects each session to be initiated via one mode, not both. The Application-layer `BeginSignPdfAsync` records a session marked `Mode = Webhook`; the slice 1 polling facade (`SignPdfAsync`) does not register a webhook session. If a webhook arrives for a transaction initiated via the slice 1 polling facade (no webhook session), it is treated as `UnknownTransaction`; no mid-flight downgrade or upgrade.
- **MISA delivers a webhook for a transaction that was already finalized via slice 1 polling** (consumer mid-migration) → identical to the `UnknownTransaction` case, since no webhook session was recorded. The consumer's signed PDF was already produced by the polling path; the webhook is informational only.
- **`extraData` carries arbitrary opaque content** → SDK does NOT parse or interpret `extraData`; it forwards the raw object verbatim to the consumer's delivery hook so the consumer can use any out-of-band correlation it sent at session-start time. SDK does not log `extraData` contents (the consumer may have placed PII there).
- **Non-PDF formats** — when slice 3 has shipped (XML, Word, Excel facades), the slice 4 webhook path MUST finalize using the format-specific `/documents/attachment` shape recorded on the session by `BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync`. The webhook envelope itself is format-agnostic; format dispatch happens via the session record.
- **Transport, refresh-on-401, single-flight refresh** — the SDK's outbound `/documents/attachment` call from the webhook handler runs through the same slice 1 HTTP plumbing (auth refresh, transport retry, correlation ID) as the synchronous path. No new transport semantics.
- **Duplicate webhook delivery of an envelope-status `FAILED` or `CANCELLED`** → first delivery returns a success ACK + invokes the consumer's delivery hook exactly once with `TerminalWithoutFinalize` (per FR-083). The success ACK + terminal-outcome are cached on the session record. Subsequent duplicates short-circuit to the cached success ACK and do NOT re-invoke the delivery hook (Clarifications Session 2026-05-24).
- **Webhook endpoint receives a body that is not JSON** (e.g. MISA's gateway returns an HTML error page that mistakenly POSTs back) → handler returns a typed `MalformedEnvelope`-class ACK; the endpoint returns it as a `{ errorCode, devMsg, userMsg }` 200 response (per FR-085).
- **Forged POST to the bare webhook path when a secret is configured** → routed to `404 Not Found` by the routing layer before the webhook handler runs (FR-099); no envelope parsing, no log line that leaks the configured secret.
- **POST from a non-allowlisted IP when `AllowedIps` is configured** → returned as `403 Forbidden` before the webhook handler runs (FR-100); structured WARN log line with correlation ID and IP class only, never the full IP at INFO/DEBUG.

## Requirements *(mandatory)*

### Functional Requirements

Slice 3's last `FR-NNN` is `FR-070`; this slice picks up at `FR-075` with room to grow.

**Public surface — initiate a webhook-mode sign**

- **FR-075**: `IMisaESignClient` MUST expose one new initiation facade per supported format alongside slice 1's and slice 3's blocking facades: `BeginSignPdfAsync` (PDF, mandatory in this slice); `BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync` (the three non-PDF formats from slice 3, mandatory in this slice because slice 4 ships after slice 3 is merged per the parent plan). Each `Begin…Async` MUST accept the same input shape as its synchronous counterpart from slice 1 / slice 3 (source document + signing context). Note: MISA's documented `/Signing/hash` request body has no consumer-supplied correlator field, so the SDK does NOT accept an `extraData` argument on the Begin call (Clarifications Session 2026-05-23). MISA's webhook envelope carries an `extraData` object, but it is opaque content MISA may attach server-side; the SDK forwards it to the consumer's delivery hook untouched.
- **FR-076**: Each `Begin…Async` MUST run the slice 1 / slice 3 pipeline up to and including `/Signing/hash`, MUST NOT poll `/Signing/status`, and MUST register a `SigningSession` record in `ISigningSessionStore` (see FR-079) IMMEDIATELY AFTER the `/Signing/hash` response is received and BEFORE the facade returns its `BeginResult` to the caller — so the session's primary key `(clientId, transactionId)` is bound to the MISA-issued `transactionId`. (Clarifications Session 2026-05-24.) If the `/Signing/hash` call fails, no session record is created. Webhook deliveries that race the `/Signing/hash` response unwind (i.e. MISA's push arrives before `RegisterAsync` completes) surface as `UnknownTransaction` per FR-082; MISA's natural webhook-retry replays the delivery after the session is registered. The returned value carries the MISA-issued `transactionId` and the format the session was initiated for; it does NOT carry a `messageId` because MISA generates `messageId` server-side and only delivers it on the webhook envelope.
- **FR-077**: The new `Begin…Async` facades MUST coexist with slice 1's `SignPdfAsync` / slice 3's blocking `SignXmlAsync` / `SignWordAsync` / `SignExcelAsync`. The blocking facades retain slice 1's polling behavior unchanged (`FR-011` / slice 1's polling state machine). The webhook and polling paths share no session record — a webhook arriving for a transaction initiated via the polling path is treated as `UnknownTransaction` per FR-082.
- **FR-078**: The Begin facades and the webhook handler MUST be safe for concurrent use as a DI singleton, matching slice 1's `FR-027` contract. The `ISigningSessionStore` adapter contract MUST be safe under concurrent register + lookup + finalize for the same `transactionId`; finalize MUST be single-flight per `transactionId` so a duplicate webhook delivery during the first finalize awaits its result rather than triggering a second `/documents/attachment` call.

**Signing-session bookkeeping**

- **FR-079**: System MUST introduce a swappable `ISigningSessionStore` port at the Application layer. Each session record MUST capture: `transactionId` (MISA-issued, populated after `/Signing/hash` succeeds; the session's primary key alongside `clientId`); the source document(s) and the `/documents/hash` response payload required to compose a `/documents/attachment` call (per slice 3's `FR-053` per-format response field set); the requested `DocumentFormat` (slice 3's `DocumentFormat` enum); the configured `clientId`; the SDK creation timestamp (from `ISystemClock`); the configured TTL (Assumption 4); the set of MISA-supplied `messageId` values observed on this session (initially empty; populated on every webhook delivery — success or failure); and an optional cached **success** ACK + cached signed-bytes payload populated AFTER the first **successful** finalize completes (for idempotency per FR-080). Failure ACKs from finalize attempts MUST NOT be cached on the session record. The default adapter MUST be in-memory and MUST evict records past their TTL on read; consumers register a distributed adapter (e.g. Redis, SQL) by binding their own `ISigningSessionStore` before `AddMisaConnectESign`.
- **FR-080**: When a webhook envelope arrives, System MUST look up the session by `(clientId, transactionId)`. If no record matches, System MUST surface a typed `UnknownTransaction` per FR-082 — the SDK MUST NOT use the inbound `messageId` to attempt a fallback lookup (MISA generates `messageId` server-side; the SDK never knows it before the first webhook delivery). If the matching record carries a cached **success** ACK + cached signed-bytes payload (a previous finalize succeeded), System MUST add the inbound `messageId` to the observed-set, return the cached success ACK, and MUST NOT invoke `/documents/attachment` again — regardless of whether the inbound `messageId` was previously observed. `transactionId` is the canonical identity of the work-unit and only the first **successful** finalize per `transactionId` is authoritative. The consumer's delivery hook MUST NOT be invoked for any delivery that hits a cached success. This is the SDK's only idempotency guarantee — and it applies ONLY to successful finalizes.
- **FR-081**: When the matching session record exists but has no cached success yet (either no finalize has been attempted, or all previous finalize attempts failed), System MUST run the finalize path (compose `/documents/attachment` per slice 3's `FR-056` using the session's recorded per-format payload + the webhook's `signatures[]`), record the triggering `messageId` on the session's observed-set regardless of outcome, and on **success** invoke the consumer's delivery hook exactly once and cache the success ACK + signed-bytes per FR-079. On **failure** (transport budget exhausted, MISA 4xx/5xx, or any thrown exception from the finalize path), System MUST return a failure ACK to the caller, MUST NOT cache the failure on the session record, MUST NOT invoke the consumer's delivery hook, and MUST leave the session record otherwise unchanged so that a subsequent MISA webhook delivery for the same `transactionId` triggers a fresh finalize attempt. Finalize MUST be single-flight per `(clientId, transactionId)` per FR-078; concurrent deliveries with the same `transactionId` (whether the same `messageId` or different) MUST await the first in-flight finalize and reuse its result — success caches it, failure does not.
- **FR-081a**: A session record's lifetime is bounded by its TTL (Assumption 4). When MISA's natural webhook retries continue past `Session.Ttl` without producing a successful finalize, the next inbound delivery MUST surface as `UnknownTransaction` because the session was already evicted by the store. The retry budget for a transient `/documents/attachment` failure is therefore "however many webhook deliveries MISA fits within `Session.Ttl`", not a separately configured count. Consumers needing a larger retry window override `Session.Ttl`.

**Webhook envelope validation**

- **FR-082**: The Application-layer webhook handler MUST validate every inbound envelope in this order, returning a typed error ACK on the first failure:
  1. **Shape**: the body parses against the MISA-documented schema `{ messageId, clientId, extraData, status, errorCode, transactionId, signatures: [{ documentId, signature }] }` per §3.8 / §4.9 of the API doc. Missing required fields, wrong types, or non-JSON content → typed `MalformedEnvelope`.
  2. **Client identity**: `clientId` matches the configured `Misa:ESign:ClientId` exactly (case-sensitive). Mismatch → typed `ClientIdMismatch`.
  3. **Session existence**: a session record matches `(clientId, transactionId)` in `ISigningSessionStore` AND is unexpired per its TTL. Otherwise → typed `UnknownTransaction`. The inbound `messageId` is NOT used for session lookup (MISA generates it server-side; the SDK first observes it on this delivery).
  4. **Status-specific shape**: if `status = SUCCESS`, `signatures[]` MUST be non-empty AND every entry's `documentId` MUST match one of the document IDs the session recorded at `/documents/hash` time. Otherwise → typed `IncompleteSuccessEnvelope` (empty signatures) or `DocumentIdMismatch` (unknown documentId).
  Each typed error MUST carry MISA's correlation ID (propagated from the inbound HTTP request — see FR-086), the matched `transactionId` if any, and a `Format` property of slice 3's `DocumentFormat` enum (set to `Unknown` only when validation failed before the session was resolved). Field names in the validated payload MUST match MISA's published shape verbatim (Constitution Principle IV); the SDK MUST NOT silently coerce casing (Postman collection is the tie-breaker if the doc and wire disagree).
- **FR-083**: For `status = FAILED` or `status = CANCELLED` envelopes that pass shape + client-identity + session-existence checks, System MUST NOT call `/documents/attachment`. The handler MUST invoke the consumer's delivery hook EXACTLY ONCE with a typed terminal-state result carrying MISA's `errorCode`, `transactionId`, and the requested `DocumentFormat`. The ACK returned to MISA MUST be a success ACK (per Assumption 6) — the webhook was successfully received and the SDK's bookkeeping was correctly updated; MISA's transaction-level failure is reported to the consumer via the delivery hook, not via the ACK. On the first terminal-status delivery, System MUST cache the success ACK + the typed terminal-state outcome on the session record (using the same cache slot as FR-080 / FR-079). Duplicate subsequent deliveries for the same `transactionId` (whether the same or a fresh `messageId`) MUST short-circuit to the cached success ACK and MUST NOT re-invoke the consumer's delivery hook (Clarifications Session 2026-05-24). This extends the "exactly-once delivery to the consumer per `(clientId, transactionId)`" guarantee from FR-080 to terminal-status outcomes; the cached envelope is a success ACK so this remains consistent with FR-081's "failure ACKs are NEVER cached".

**Acknowledgement shape**

- **FR-084**: The Application-layer webhook handler MUST return an ACK envelope of shape `{ errorCode, devMsg, userMsg }` per §4.9 of the API doc, with field names and casing matching MISA's published shape verbatim. The handler MUST NOT add fields MISA's doc does not name.
- **FR-085**: The sample API's minimal-API webhook endpoint at `samples/MisaConnect.Samples.Api/` MUST return HTTP `200 OK` for every well-formed `POST` regardless of the handler's typed result, with the ACK envelope as the JSON body. Rationale: MISA's documented contract uses the ACK body for status — see §4.9 "Response".

### Key Entities

- **Signing Session** — captured at `Begin…Async` time, recorded in `ISigningSessionStore`. Fields: `transactionId` (MISA-issued, post-`/Signing/hash`; primary key alongside `clientId`), `clientId` (configured), `documentFormat` (`DocumentFormat` enum from slice 3), per-format `/documents/hash` response payload, recorded document IDs, creation timestamp, TTL, set of observed MISA-supplied `messageId` values (initially empty; appended on each webhook delivery), cached ACK + signed-bytes payload (populated on first finalize for idempotency).
- **Webhook Envelope** — the inbound MISA-shaped body: `{ messageId, clientId, extraData, status, errorCode, transactionId, signatures: [{ documentId, signature }] }` per §3.8 / §4.9. `messageId` is MISA-generated; the SDK first observes it on the inbound delivery. Parsed into a typed Domain model; `extraData` carried as an opaque `IReadOnlyDictionary<string, object?>` or equivalent — never logged.
- **ACK Envelope** — the outbound MISA-shaped response: `{ errorCode, devMsg, userMsg }` per §4.9. Field names match MISA verbatim.
- **Begin Result** — the value returned by `Begin…Async` to the consumer: `{ TransactionId, Format }` (Domain record property names). The consumer uses these to correlate the future webhook delivery against its own state. The MISA-supplied `messageId` is not part of this result because MISA does not issue it until the webhook fires.
- **Webhook Outcome** — the typed result the Application-layer handler passes to the consumer's delivery hook: success-with-signed-bytes (carrying `transactionId`, `documentFormat`, signed-document bytes), failure-with-error (carrying `transactionId`, MISA `errorCode`, typed validation-failure category), or terminal-status-without-finalize (`FAILED` / `CANCELLED` per FR-083). Each variant carries the correlation ID.
- **`ISigningSessionStore`** — the new Application-layer port introduced by this slice. Methods (minimum): `RegisterAsync(SigningSession)`, `TryGetByTransactionIdAsync(clientId, transactionId)`, `RecordObservedMessageIdAsync(clientId, transactionId, messageId)`, `CacheSuccessAsync(clientId, transactionId, triggeringMessageId, ackEnvelope, signedBytes?)`. Note: `CacheSuccessAsync` caches both successful-finalize ACKs (FR-080) AND terminal-status success ACKs from envelope-status `FAILED` / `CANCELLED` (FR-083); `signedBytes` is null for terminal-status entries. Failure ACKs from finalize attempts are NEVER cached (FR-081). Default adapter is in-memory + TTL-based eviction; durable adapters are out of scope (parent prompt).

## Assumptions

1. **One Begin facade per format.** Slice 4 ships `BeginSignPdfAsync` plus the three slice-3 format counterparts (`BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync`), since the slice runs after slice 3 is merged per `docs/misa-esign-spec-plan.md`. Rationale: matches slice 1's per-format facade convention; gives webhook-mode parity with the blocking path; avoids a polymorphic `BeginSignAsync(format, …)` and the "wrong-arm-of-the-union" bug class slice 3 explicitly rejected.
2. **Webhook mode and polling mode coexist by default.** `MisaESignOptions.Webhook.Mode = Both` is the default; consumers explicitly opt one mode out via configuration (FR-093). Rationale: lets consumers migrate one call site at a time without forcing a global cutover; the parent plan describes the webhook as "an alternative to polling", not a replacement.
3. **No new ports beyond `ISigningSessionStore`.** The slice reuses slice 1's `ITokenCache`, `ITokenCacheKeySelector`, `ICertificateSelector`, `ICorrelationIdAccessor`, `ISystemClock`, and slice 3's `DocumentFormat`. The only new Application-layer port is `ISigningSessionStore`. Default adapter is in-memory with TTL eviction; durable adapters are out of scope per the parent prompt ("durable webhook queueing").
4. **Default `Session.Ttl` is 24 hours.** (Confirmed in Clarifications Session 2026-05-23.) A session record lives for `24:00:00` (one wall-clock day) by default, configurable via `Misa:ESign:Webhook:Session:Ttl` as a standard .NET `TimeSpan`. The default is **decoupled** from slice 1's `MisaESignOptions.SignTimeout` (which is a polling-mode budget measured in seconds and is unrelated to how long MISA may keep retrying webhook deliveries on transient finalize failures). 24h matches the order of magnitude used by comparable webhook platforms (Stripe, GitHub, Twilio): long enough for MISA to retry through transient outages bounded by a business day; short enough to cap default in-memory store growth at one day's signing throughput. Once evicted, late webhook deliveries surface as `UnknownTransaction` per FR-082 — the consumer's responsibility to size the TTL upward if their MISA-side retry profile demands more than 24h.
5. **Webhook registration is consumer-side and out-of-band with MISA.** Per the parent prompt and §3.8 of the API doc, MISA accepts the consumer's webhook URL through MISA's own onboarding process, not via an API call. The SDK does NOT register, discover, or validate the configured webhook URL against MISA; if a consumer's webhook URL changes, they update it with MISA directly. The slice's `[SandboxFact]` per FR-097 skips when no webhook URL is configured because there is no SDK call that would register it.
6. **Success ACK uses `errorCode = "0"`.** MISA's §4.9 documents the ACK shape `{ errorCode, devMsg, userMsg }` but does not enumerate canonical success/failure codes. The SDK uses `errorCode = "0"` for success ACKs (matches the eInvoice ecosystem's success-code convention used elsewhere in MISA's docs) and namespaced internal codes (e.g. `"webhook.client_id_mismatch"`, `"webhook.unknown_transaction"`, `"webhook.malformed"`) for failure ACKs. The MISA Postman collection is the tie-breaker per the parent plan; if the collection specifies different sentinels, the implementation reconciles at `/speckit-plan` time.
7. **Webhook endpoint always returns HTTP 200.** Per FR-085, the sample API's webhook endpoint returns `200 OK` for every well-formed POST regardless of the handler's typed result; failure is reported via the ACK body's `errorCode`. Rationale: MISA's documented contract treats the ACK body as the status signal (§4.9), so non-`200` responses provoke MISA's transport-level retry rather than a typed application-level acknowledgement. If MISA's actual behavior diverges (Postman collection shows non-`200` semantics), the implementation reconciles at `/speckit-plan`.
8. **Session identity is `(clientId, transactionId)`; `messageId` is MISA-generated.** (Confirmed in Clarifications Session 2026-05-23.) MISA's documented `/Signing/hash` request body has no `messageId` field, so the SDK does not send one. MISA generates `messageId` server-side and only delivers it on the webhook envelope per §4.9. The SDK therefore keys sessions in `ISigningSessionStore` by `(clientId, transactionId)`, records every observed `messageId` on the session for visibility (per FR-079), and treats `messageId` purely as the post-arrival dedupe key — when a delivery's `messageId` is already present in the session's observed-set, the SDK short-circuits to the cached ACK without re-finalizing (FR-080). If MISA emits multiple distinct `messageId` values for the same `transactionId` (e.g. retry with a fresh `messageId`), the SDK still treats `transactionId` as the canonical work-unit and finalizes only once — subsequent deliveries hit the cached ACK regardless of `messageId`.
9. **`extraData` is opaque to the SDK and not consumer-controlled at Begin time.** MISA's documented `/Signing/hash` request body has no consumer-supplied `extraData` field, so the SDK does NOT accept an `extraData` argument on `Begin…Async` (FR-075). MISA's webhook envelope carries an `extraData` object that MISA may populate server-side; the SDK surfaces it to the consumer's delivery hook untouched and treats it as opaque content the consumer may use for any out-of-band purpose. The SDK does NOT parse, validate, or log `extraData` contents — MISA or any upstream system may have placed PII there. Per FR-087, `extraData` content is excluded from all log entries.
10. **Webhook handler is invoked from an existing HTTP pipeline.** The Application-layer webhook handler is a plain method (e.g. `HandleAsync(WebhookEnvelope, …)`); it is the consumer's responsibility to wire it into their HTTP framework (ASP.NET minimal API, Azure Functions, gRPC, etc.). The slice ships a minimal-API wiring in `samples/MisaConnect.Samples.Api/` (FR-094) as a reference; production consumers may copy it or write their own. The SDK does NOT take an ASP.NET dependency in the `Client` or `Application` projects.
11. **No HMAC / signature verification at the SDK layer; transport-layer defense-in-depth lives in the sample API.** MISA's §3.8 / §4.9 do not specify a webhook-signature header or HMAC scheme. Per the parent prompt's out-of-scope list, the SDK does NOT implement HMAC, signature, or timestamp-replay protection — `clientId` body matching (FR-082) is the only envelope-level authentication MISA's documented contract supports. To compensate, and per Clarifications Session 2026-05-23, the sample API at `samples/MisaConnect.Samples.Api/` enforces two optional transport-layer auth layers configurable by the consumer: a shared-secret URL segment (FR-099) and a CIDR allowlist (FR-100). These are consumer-side defense-in-depth, not MISA-mandated. Production consumers using the sample as a template should configure at least one. If the Postman collection reveals an undocumented MISA-side header (e.g. `x-misa-signature`), the implementation reconciles at `/speckit-plan` time and may add a `IWebhookSignatureVerifier` port in a follow-up slice.
12. **Out of scope (verbatim from the slice prompt)**: webhook signature / HMAC / replay protection beyond what MISA's doc specifies (none documented), durable webhook queueing, and webhook registration / discovery (registration is handled with MISA out-of-band per the doc).
13. **The constitution principles** in [.specify/memory/constitution.md](../../.specify/memory/constitution.md) — especially zero-dep Domain, port-and-adapter extensibility, wire-format fidelity (Constitution Principle IV — including MISA's spelling of `Doc_Attackment` preserved verbatim from slice 3's `FR-056`), and no-secrets/no-PII-in-logs (Constitution Principle VIII — extended to `extraData` and `signatures[].signature` per FR-087) — apply to every requirement above.
