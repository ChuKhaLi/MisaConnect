# Implementation Plan: MISA eSign — Webhook Receiver

**Branch**: `004-misa-esign-webhook` | **Date**: 2026-05-23 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/004-misa-esign-webhook/spec.md`

## Summary

Slice 4 of the `MisaConnect.ESign` product family. It adds the **only async-completion alternative** to slice 1's `/Signing/status` polling loop: MISA POSTs a `{ messageId, clientId, extraData, status, errorCode, transactionId, signatures[] }` envelope to a partner-hosted endpoint when a signing transaction reaches a terminal state, and the SDK reconciles that envelope to an in-flight `SigningSession` and finalizes the signed document by calling `/documents/attachment` (slice 1's existing wire boundary, with slice 3's per-format shaping). The slice splits each existing blocking facade — `SignPdfAsync` / `SignXmlAsync` / `SignWordAsync` / `SignExcelAsync` — into a new non-blocking initiation facade (`BeginSignPdfAsync` / `BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync`) that runs steps 1–5 of slice 1's pipeline (login → cert select → hash → register session → `/Signing/hash`) and a webhook-driven finalize path that runs step 7 (attachment) on the consumer's webhook endpoint. The blocking facades from slices 1+3 stay intact (FR-077, FR-089). One new Application-layer port lands — `ISigningSessionStore` — with an in-memory + TTL-eviction default adapter and the canonical session record (`transactionId` primary-keyed by `clientId`; per-format hash payload; observed-set of MISA-supplied `messageId` values; cached **success** ACK + signed bytes; failures NEVER cached per FR-081). The Application-layer webhook handler (`HandleWebhookAsync`) performs the four-step validation (shape → `clientId` match → session existence → status-specific shape per FR-082), runs the finalize path single-flight per `(clientId, transactionId)` (FR-078), and returns the documented `{ errorCode, devMsg, userMsg }` ACK envelope. The sample API at `samples/MisaConnect.Samples.Api/` ships a minimal-API endpoint wired to the handler with two configurable transport-layer auth layers — a shared-secret URL segment (FR-099, `Misa:ESign:Webhook:Secret`) and a CIDR allowlist (FR-100, `Misa:ESign:Webhook:AllowedIps`) — plus a startup WARN line when neither is configured (FR-101). New `MisaESignOptions.Webhook` sub-section adds `Mode` (`Polling` | `Webhook` | `Both`, default `Both`) and `Session.Ttl` (`TimeSpan`, default `24:00:00`); webhook-mode and polling-mode coexist by default so consumers migrate per-call-site without a global cutover (Assumption 2). The Application layer reuses 100% of slice 1's auth (`EnsureAccessToken`, `ListActiveCertificates`, `SubmitSignHash`), slice 3's per-format `AttachSignatureTo{Pdf,Xml,WordExcel}` use cases, the existing `ESignErrorMapper`, the per-format `Format` discriminator on every typed exception (FR-062 from slice 3 carries through), and `ESignLogScrubber` (extended only to redact webhook-envelope `signatures[].signature` and the `Misa:ESign:Webhook:Secret` configured value). The slice extends both test suites — unit tests cover envelope parsing, the four-step validation order, single-flight finalize under concurrent deliveries, the failure-not-cached / success-cached contract, cross-format webhook finalize across all four formats, and the sample-API auth layers (secret URL routing + CIDR matching + startup WARN); integration tests drive the sample API end-to-end with the in-repo `EsignFake` server's new webhook-driver helper (synthesizes MISA-shaped POSTs against the sample's webhook URL) and add one `[SandboxFact]` for the real-MISA round-trip (skips when no webhook URL is registered or sandbox env vars are absent, per Assumption 5). Slice 1's PDF blocking happy path (`SC-001`) and slice 3's multi-format happy path (`SC-015`) are preserved byte-identically (FR-089, FR-091, SC-032). Public-surface additions are catalogued in [contracts/public-surface.md](./contracts/public-surface.md); slice 4 ships as `2.0.0-preview.4`.

## Technical Context

**Language/Version**: C# 12 / .NET 8.0 (unchanged from slices 1+2+3 — `Directory.Build.props` pins `TargetFramework=net8.0`, `Nullable=enable`, `TreatWarningsAsErrors=true`).

**Primary Dependencies**: No new packages on the production SDK. The slice reuses slice 1's `System.Net.Http` typed `HttpClient` + `IHttpClientFactory`, `Microsoft.Extensions.{Configuration,DependencyInjection,Http,Options,Logging.Abstractions}`, and `System.Text.Json` for wire serialization. The new typed-Domain webhook envelope + ACK envelope DTOs land alongside the existing wire DTOs in `Infrastructure/ESign/Wire/` and are parsed with the same `ESignJsonOptions.Wire` settings. The sample API (`samples/MisaConnect.Samples.Api/`) reuses the existing ASP.NET Core 8 minimal-API + `IHttpContextAccessor` plumbing it already has for the eInvoice endpoints; the new CIDR allowlist (FR-100) is implemented with `System.Net.IPNetwork` (built into .NET 8) — **no new NuGet dependencies in either the SDK or the sample**.

**Storage**: None on disk. `SigningSession` records live in the registered `ISigningSessionStore` adapter — default is an in-memory `ConcurrentDictionary<(string ClientId, string TransactionId), SigningSession>` with TTL-eviction-on-read (a single background eviction sweep is **out of scope** — the SDK is host-agnostic and doesn't own a timer; consumers needing proactive eviction either register a distributed adapter that bounds its own size, or trust read-time eviction + bounded session creation rate). Sessions carry the per-format `/documents/hash` response payload (the bytes that have to be threaded into `/documents/attachment` per slice 3's `FR-053` / `FR-056`) so the finalize-from-webhook path has everything it needs without re-calling MISA. The slice-1 `ITokenCache` is reused as-is — neither format nor session identity is part of the cache key (slice 1's `FR-026` unchanged); one cached token covers polling-mode and webhook-mode calls for the same user.

**Testing**: xUnit. Slice-4 unit tests land in two new subfolders under `tests/MisaConnect.ESign.UnitTests/`: `Webhook/` (envelope parsing, four-step validation order, single-flight finalize, failure-not-cached contract, cross-format finalize, `status = FAILED|CANCELLED` handling, observed-`messageId` bookkeeping) and `Sessions/` (the `InMemorySigningSessionStore` adapter's concurrency + TTL contract). New integration tests land in `tests/MisaConnect.ESign.IntegrationTests/EndToEnd/` (sample-API end-to-end happy path + dedupe + failure-then-success across the four formats) plus `tests/MisaConnect.ESign.IntegrationTests/SampleApi/` (a new subfolder for the sample-API auth-layer tests: secret-URL routing, CIDR allowlist, startup-WARN log scan). One new `[SandboxFact]` lands under `tests/MisaConnect.ESign.IntegrationTests/Sandbox/SignViaWebhookSandboxTests.cs` gated by `MISACONNECT_ESIGN_SANDBOX_*` + a new `MISACONNECT_ESIGN_SANDBOX_WEBHOOK_URL` env var (the consumer-registered URL with MISA per Assumption 5). The in-repo `EsignFake/FakeMisaESignServer.cs` gets a new test-driver helper (`PostSyntheticWebhookAsync(transactionId, …)`) plus a callable `/documents/attachment` request counter for `SC-026` / `SC-026a` / `SC-031` assertions. Unit-suite budget per the constitution: `< 30s` total — slice 4 inherits this and the cumulative unit suite (slices 1+2+3+4) must continue to honor it (SC-033).

**Target Platform**: NuGet class libraries (`MisaConnect.ESign.{Domain,Application,Infrastructure,Client}`) consumed by .NET 8 hosts. The sample API targets ASP.NET Core 8 minimal-API. The SDK itself takes **no ASP.NET dependency** — the Application-layer webhook handler is a plain method (`HandleWebhookAsync(WebhookEnvelope, CancellationToken)`) that the consumer wires into their HTTP framework of choice (Assumption 10). The sample's minimal-API wiring is a reference implementation, not part of the SDK surface.

**Project Type**: Layered class-library product family slice 4. No new csproj on the SDK side — slice 4 adds files to the four existing `MisaConnect.ESign.*` projects and the two test projects. One new namespace family lands per existing project (`Application.Webhook`, `Infrastructure.ESign.Webhook`, `Client.Webhook`). The sample API (`samples/MisaConnect.Samples.Api/`) gains a new `Endpoints/ESignWebhookEndpoint.cs` parallel to the existing `InvoiceEndpoints.cs` / `TemplateEndpoints.cs` files.

**Performance Goals**: No throughput target. The webhook-mode path is purely additive on top of slice 1's HTTP plumbing; the per-call latency budget is the slice-1 `/documents/attachment` budget unchanged. Finalize single-flight (FR-078) introduces a per-`(clientId, transactionId)` semaphore on the in-memory session store — under contention, parallel duplicate deliveries await the first finalize (which already holds the per-key lock) rather than racing. Memory overhead is one session record per in-flight Begin call (≈ a few KB per record including the hash payload), bounded by `Session.Ttl × signing-rate`; at the default 24h TTL a consumer signing 1000 docs/day holds ≤ 1000 in-flight records — well within any plausible bound.

**Constraints**:

- Constitution-bound: `Domain` zero external deps (the new `Domain.Webhook.WebhookEnvelope` + `WebhookStatus` + `WebhookOutcome` + `BeginResult` records and the `Domain.Sessions.SigningSession` record are Domain-pure); `Application` Domain + `Microsoft.Extensions.Logging.Abstractions` only; Infrastructure `internal` except DI/options/port-interfaces (the new `ISigningSessionStore` port lives in Application; the in-memory adapter `InMemorySigningSessionStore` lives in Infrastructure and stays `internal` — DI binding registers the interface, not the concrete type). Slice 4 introduces no new layer-crossing.
- Logs MUST NOT contain raw `signatures[].signature` values, `documentBytes`, `digest`, `documentHash`, `mainDom`, `sh`, `signatureId`, certificate private-key material, the `AuthorizationRM` header, `extraData` content, or the configured `Misa:ESign:Webhook:Secret` (FR-087, FR-099). The `ESignLogScrubber` gains two new JSON-path matchers: on inbound webhook envelopes, `$.signatures[*].signature` and `$.extraData` are redacted; on the structured-logging values emitted by the webhook handler, the `IPAddress` field is reduced to a class label (`"public"` / `"private-rfc1918"` / `"loopback"`) per FR-100. The Webhook Secret is never read into a log message at any level — it lives in the configuration object only, and the routing layer references it by routing-pattern construction.
- Wire DTOs match MISA's published shape verbatim per Principle IV. The webhook envelope DTO mirrors MISA §3.8 / §4.9 `{ messageId, clientId, extraData, status, errorCode, transactionId, signatures: [{ documentId, signature }] }`; the ACK DTO mirrors §4.9 `{ errorCode, devMsg, userMsg }`. Inbound field-name casing matches MISA's documented JSON exactly (camelCase per §4.9); the SDK does NOT silently coerce casing (Constitution Principle IV; FR-082). On the outbound side, only the ACK envelope's three documented fields are sent — no additional fields per FR-084.
- The webhook handler's outbound `/documents/attachment` call inherits slice 1's `ClientHeadersHandler` (x-clientId / x-clientKey injection), `RemoteSigningAuthHandler` (AuthorizationRM injection, 401 refresh-and-retry, single-flight), `TransientFailureRetryHandler` (bounded 5xx/429/timeout retry), and `ICorrelationIdAccessor` (correlation ID on every request + every surfaced error). No new HTTP-layer behavior on the outbound side. The inbound correlation ID is sourced from the standard ASP.NET correlation header if present, generated otherwise (FR-086).
- Correlation IDs are mandatory and structured on every new log entry, every surfaced typed error from the webhook handler, and every result passed to the consumer's delivery hook (FR-086, FR-088).

**Scale/Scope**: Four new public facade methods on `IMisaESignClient` (`BeginSignPdfAsync` / `BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync`), one new public webhook handler facade (`HandleWebhookAsync(WebhookEnvelopeDto, CancellationToken)` returning a typed `WebhookHandleResultDto` carrying the ACK envelope to return to MISA), one new Domain enum (`WebhookStatus { Success, Failed, Cancelled }`), four new Domain records (`WebhookEnvelope`, `WebhookOutcome`, `BeginResult`, `SigningSession`), one new typed exception family for webhook-validation failures (`WebhookValidationException` with discriminated subtypes `MalformedEnvelope`, `ClientIdMismatch`, `UnknownTransaction`, `IncompleteSuccessEnvelope`, `DocumentIdMismatch`), one new Application-layer port (`ISigningSessionStore`), one new Application-layer use case (`HandleWebhook`) orchestrating the four-step validation + single-flight finalize, four new Application-layer use cases (`BeginSignPdf` / `BeginSignXml` / `BeginSignWord` / `BeginSignExcel`) factored from slices 1+3's existing orchestrators, one new Infrastructure-layer adapter (`InMemorySigningSessionStore`), DI registrations for all of the above, options extension (`MisaESignOptions.Webhook` sub-section with `Mode` + `Session.Ttl`), two new sample-API endpoints (the webhook receiver `MapPost("…/esign/webhook[/{secret}]")` + a startup-time WARN emitter), three new Client DTOs (`BeginSignPdfResultDto` / per-format variants `BeginSignXmlResultDto` / `BeginSignWordResultDto` / `BeginSignExcelResultDto` — each carries `transactionId` + `documentFormat`), and one new `WebhookEnvelopeDto` + `WebhookAckDto` + `WebhookHandleResultDto` set. Expected new code: ~2400–3000 LoC including tests and sample-API endpoint and `EsignFake` extensions. No new csproj on the SDK or sample side.

**Structure Decision**: Slice 4 is a strict **extension** of the slice-1/2/3 layout — no new csproj, no namespace reshuffles, no copying of HTTP plumbing. The only structural addition is the `Application.UseCases.BeginSign{Pdf,Xml,Word,Excel}` factoring: each existing blocking `Sign{Format}` orchestrator is refactored to be a composition of `BeginSign{Format}` (steps 1–5: login → cert select → hash → register session → submit `/Signing/hash`) + `PollSignStatus` (slice 1's polling state machine, unchanged) + `AttachSignature{Format}` (slice 3's per-format finalize call, unchanged). The webhook-driven path runs the same `BeginSign{Format}` step then skips `PollSignStatus` and lets the webhook handler trigger `AttachSignature{Format}` via the `FinalizeFromWebhook` orchestrator. This factoring preserves byte-identical observable behavior on the blocking paths (FR-089 / FR-091) and gives the webhook path 100% shared plumbing with slice 1 / slice 3. The `ISigningSessionStore` port is the only new Application-layer port and lives next to slice 1's `ITokenCache`; its in-memory default adapter sits in `Infrastructure.Sessions/` (a new namespace that follows the slice-1 pattern of `Infrastructure.Caching/` for `InMemoryTokenCache`). The sample API endpoint at `samples/MisaConnect.Samples.Api/Endpoints/ESignWebhookEndpoint.cs` is the only host-side addition; it mirrors the existing `InvoiceEndpoints.cs` / `TemplateEndpoints.cs` pattern and reads its configuration from the same `Misa:ESign:Webhook` section the SDK reads, ensuring there's exactly one source of truth for `Mode`, `Path`, `Secret`, `AllowedIps`, and `Session.Ttl`.
