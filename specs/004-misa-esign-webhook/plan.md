# Implementation Plan: MISA eSign — Webhook Receiver

**Branch**: `004-misa-esign-webhook` | **Date**: 2026-05-23 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/004-misa-esign-webhook/spec.md`

## Summary

Slice 4 of the `MisaConnect.ESign` product family and the final slice before the `2.0.0` cut. It introduces the only asynchronous completion path for the SDK's signing pipeline as an alternative to slice 1's `/Signing/status` polling loop: MISA POSTs the documented webhook envelope (`{ messageId, clientId, extraData, status, errorCode, transactionId, signatures: [{ documentId, signature }] }` per §3.8 / §4.9) to a partner-hosted endpoint when every document in a transaction is signed successfully (or when the transaction terminates with `FAILED` / `CANCELLED`), and the SDK reconciles the inbound delivery against an in-flight signing session, calls `/documents/attachment` to produce the final signed bytes, and surfaces the result to a consumer-supplied delivery hook. The slice ships in five layers: (a) **four new non-blocking initiation facades** on `IMisaESignClient` (`BeginSignPdfAsync`, `BeginSignXmlAsync`, `BeginSignWordAsync`, `BeginSignExcelAsync`) that reuse the slice-1 / slice-3 pipeline up to and including `/Signing/hash`, register a `SigningSession` record in a new `ISigningSessionStore` Application-layer port (default in-memory adapter with TTL-based eviction), and return a `BeginResultDto { TransactionId, Format }` to the consumer — without polling; (b) **the `WebhookHandler` Application use case** that runs the four-step validation pipeline (shape → clientId → session → status-shape) per FR-082, the finalize-and-cache state machine per FR-080 / FR-081 / FR-083, and the single-flight finalize guarantee per FR-078 (via a separate `IFinalizeLockOwner` port); (c) **the new `Domain.Sessions` and `Domain.Webhook` types** (`SigningSession`, `PerFormatHashPayload`, `SigningSessionCachedSuccess`, `WebhookEnvelope`, `WebhookSignature`, `WebhookStatus`, `WebhookAck`, `BeginResult`, `WebhookOutcome` with its three sealed variants `SuccessWithSignedBytes` / `FailureWithError` / `TerminalWithoutFinalize`), the `WebhookValidationException` family (five sealed subclasses for `MalformedEnvelope` / `ClientIdMismatch` / `UnknownTransaction` / `IncompleteSuccessEnvelope` / `DocumentIdMismatch`), and the `IWebhookDeliveryHook` consumer-implementable contract; (d) **a new `MisaESignOptions.Webhook` sub-section** carrying `Mode` (`Polling` | `Webhook` | `Both`, default `Both`), `Session.Ttl` (default `24:00:00`), `Path`, `Secret` (shared-secret URL segment per FR-099), and `AllowedIps` (CIDR allowlist per FR-100) — with startup-time validation rules (`Secret` ≥ 32 chars; `Session.Ttl` ∈ [1 minute, 30 days]; every `AllowedIps` entry parses as a valid CIDR); (e) **the sample API webhook endpoint** at `samples/MisaConnect.Samples.Api/Endpoints/EsignWebhookEndpoint.cs` paralleling the existing `MapTemplateEndpoints` / `MapInvoiceEndpoints` pattern, wired through configurable shared-secret routing + optional CIDR allowlist, returning 200 on every well-formed POST with the ACK envelope as the JSON body (FR-085), emitting the FR-101 startup WARN when no transport-layer auth is configured, and shipping a commented-out `ForwardedHeadersOptions` example + a security-note README paragraph for consumers behind reverse proxies (Clarifications Session 2026-05-24). The slice extends both test suites: unit tests cover envelope parsing, the four-step validation order, duplicate-delivery short-circuit (FR-080), terminal-status duplicate handling (FR-083), single-flight finalize under concurrent identical deliveries (FR-078), the four `BeginSign{Format}Async` facades' record-then-call ordering (FR-076), cross-format finalize (one Begin per format + one synthetic webhook each, asserting the format-specific `/documents/attachment` shape per slice-3 FR-056), and slice-2's 2FA contract continuing to hold through `BeginSignPdfAsync` (FR-090 / SC-038); integration tests drive the sample API's webhook endpoint with synthetic MISA-shaped payloads (FR-096 / SC-025), assert the CIDR allowlist + secret-URL routing semantics (FR-099 / FR-100), include a `[SandboxFact]` end-to-end against real MISA (FR-097 / SC-034), and re-run slice-1 + slice-3 happy-path tests unchanged to verify FR-089 / FR-091 / SC-032. The slice-1 PDF blocking path and slice-3 multi-format blocking paths remain byte-identically preserved — the only slice-1/3-touching change is an internal refactor (extract a private `BeginSign{Format}Core` helper from each existing orchestrator that the new webhook facade reuses; the blocking facade keeps composing the helper inline). Public-surface additions are catalogued in [contracts/public-surface.md](./contracts/public-surface.md); slice 4 ships as `2.0.0-preview.4` (the last pre-release before the `2.0.0` stable cut).

## Technical Context

**Language/Version**: C# 12 / .NET 8.0 (unchanged from slices 1+2+3 — `Directory.Build.props` pins `TargetFramework=net8.0`, `Nullable=enable`, `TreatWarningsAsErrors=true`).
**Primary Dependencies**: No new packages. Slice 4 reuses the slice-1/2/3 `System.Net.Http` typed `HttpClient` + `IHttpClientFactory`, `Microsoft.Extensions.{Configuration,DependencyInjection,Http,Options,Logging.Abstractions}`, and `System.Text.Json` for wire serialization via `ESignJsonOptions.Wire`. The new webhook-envelope DTOs land in a new `Infrastructure/ESign/Webhook/WebhookDtos.cs` file. CIDR-allowlist matching uses .NET 8's built-in `System.Net.IPNetwork` (no third-party dependency per [research.md R-10](./research.md#r-10-cidr-allowlist--forwarded-headers-handling--implementation-details)). The sample API uses .NET 8's `Microsoft.AspNetCore.HttpOverrides.ForwardedHeadersOptions` (already part of the ASP.NET stack — no new package reference) for reverse-proxy forwarded-IP parsing.
**Storage**: In-process by default. The slice-4 `ISigningSessionStore` port has an in-memory default adapter (`InMemorySigningSessionStore`) using `ConcurrentDictionary<(string, string), SigningSession>` keyed by `(clientId, transactionId)` with lazy TTL-based eviction on read. Consumers needing multi-process coordination register their own adapter (Redis / SQL / EventStore / etc.) before `AddMisaConnectESign(...)`; durable-adapter implementations are out of scope per the parent prompt. The slice-1 `ITokenCache` is reused as-is — webhook mode does NOT touch token caching semantics; one cached token covers Begin + finalize for the same user.
**Testing**: xUnit. Slice-4 unit tests land in a new `Webhook/` subfolder under `tests/MisaConnect.ESign.UnitTests/` plus a `Sessions/` subfolder for the in-memory store + session-record tests. New integration tests land in `tests/MisaConnect.ESign.IntegrationTests/Webhook/` covering the sample-API endpoint flow (`WebApplicationFactory<Program>` against `samples/MisaConnect.Samples.Api/`), the CIDR-allowlist semantics, the shared-secret routing, and the `[SandboxFact]` end-to-end. The in-repo `EsignFake/FakeMisaESignServer.cs` gains a `/documents/attachment` request counter (FR-098) and a webhook-synthesizer test helper (FR-098). Unit-suite budget per the constitution: `< 30s` total — slice 4 inherits this and the cumulative unit suite (slices 1+2+3+4) must continue to honor it (SC-033).
**Target Platform**: NuGet class library consumed by .NET 8 hosts (Web API, console, worker, Azure Functions, AWS Lambda, gRPC services, MAUI). The webhook handler itself is transport-agnostic — it accepts an already-parsed `WebhookEnvelope` and returns a `WebhookAck`, so a consumer host integrates it into whatever HTTP / gRPC / message-bus framework they use ([research.md R-4](./research.md#r-4-webhook-handler--single-application-entry-point-sample-api-wires-it-into-http)). The sample API at `samples/MisaConnect.Samples.Api/` ships an ASP.NET minimal-API endpoint as a reference; the SDK proper takes no ASP.NET dependency (Constitution Principle I + Assumption 10).
**Project Type**: Layered class-library product family slice 4 — additive on top of slices 1+2+3. No new csproj. The four production projects (`MisaConnect.ESign.{Domain,Application,Infrastructure,Client}`) and two test projects already exist (created by slice 1, extended by slices 2+3); slice 4 adds files to them. The sample-API project `samples/MisaConnect.Samples.Api/` (created by the EInvoice v1 work) gains the new webhook endpoint file + a README addition.
**Performance Goals**: No throughput target for v1. Webhook-mode latency per delivery is dominated by the outbound `/documents/attachment` call to MISA — the same network hop slice 3's blocking path takes. The Begin facade's latency matches slice 1's `SignPdfAsync` minus the polling window (no `/Signing/status` calls per SC-029, so Begin returns in roughly one round-trip after `/Signing/hash`). The webhook handler's hot path (session lookup → validate → finalize → cache) issues exactly one outbound HTTP call per delivery + one in-memory store read + one in-memory store write; per-call CPU is dominated by JSON deserialization of the inbound envelope. Under concurrent identical deliveries (SC-031: at least 8 parallel), the single-flight finalize guarantee per FR-078 + [research.md R-5](./research.md#r-5-finalize-single-flight--ifinalizelockowner-lock-owner-port) caps the outbound finalize calls at exactly one per `(clientId, transactionId)`.
**Constraints**:
- Constitution-bound: `Domain` zero external deps (new types `SigningSession`, `PerFormatHashPayload`, `WebhookEnvelope`, `WebhookAck`, `BeginResult`, `WebhookOutcome` + variants, `WebhookValidationException` family are all Domain-pure); `Application` Domain + `Microsoft.Extensions.Logging.Abstractions` only (new types `WebhookHandler`, `ISigningSessionStore`, `IFinalizeLockOwner`, `IWebhookDeliveryHook`, `WebhookEnvelopeValidator` respect this); Infrastructure `internal` except DI/options/port-interfaces (the public-surface additions are catalogued in [contracts/public-surface.md](./contracts/public-surface.md)); Client public. Slice 4 introduces no new layer-crossing.
- Logs MUST NOT contain `signatures[].signature` payloads, `documentBytes` from `/documents/attachment` responses, `digest`, `documentHash`, `mainDom`, `sh`, `signatureId`, certificate private-key material, the `AuthorizationRM` header, the configured `Misa:ESign:Webhook:Secret` value, the inbound `extraData` content, the full caller IP at INFO/DEBUG, or end-user PII (FR-087 + slice-1 FR-019 + slice-3 FR-063 + the secret-as-credential rule in FR-099). The slice-1 `ESignLogScrubber` gains webhook-specific JSON-path matchers covering the inbound envelope's `signatures[*].signature` and `extraData` fields.
- Wire DTOs match MISA's published shape verbatim per Principle IV. The inbound webhook envelope mirrors §3.8 / §4.9 (`messageId` / `clientId` / `extraData` / `status` / `errorCode` / `transactionId` / `signatures[]` — camelCase with case-sensitive parsing per [research.md R-8](./research.md#r-8-webhook-envelope-wire-shape--typed-domain-record--parsing-rules)). The ACK envelope mirrors §4.9 (`errorCode` / `devMsg` / `userMsg` — camelCase). Status values are MISA's documented closed set `SUCCESS` / `FAILED` / `CANCELLED`; any other value → `MalformedEnvelopeException`.
- The webhook handler's outbound `/documents/attachment` call MUST flow through the same slice-1 HTTP plumbing (`RemoteSigningAuthHandler` for `AuthorizationRM` + 401 refresh-and-retry, `TransientFailureRetryHandler` for bounded 5xx/429/timeout retry, `ClientHeadersHandler` for `x-clientId`/`x-clientKey`, `ICorrelationIdAccessor` for correlation-ID propagation). No new transport semantics. FR-092 enforces this.
- Correlation IDs are mandatory and structured on every new log entry, every typed error, every result passed to the delivery hook (FR-086). The slice-1 `ICorrelationIdAccessor` is reused unchanged; the sample API's existing `CorrelationIdMiddleware` already populates it on every inbound HTTP request.
**Scale/Scope**: Four new public Client facades (`BeginSignPdfAsync` / `BeginSignXmlAsync` / `BeginSignWordAsync` / `BeginSignExcelAsync`) + one new public Client facade `HandleWebhookAsync` on `IMisaESignClient`. Three new Application-layer ports (`ISigningSessionStore`, `IFinalizeLockOwner`, `IWebhookDeliveryHook`). One new Application use case (`WebhookHandler`). One new Application validator (`WebhookEnvelopeValidator`). Four new Application use cases (`BeginSignPdf` / `BeginSignXml` / `BeginSignWord` / `BeginSignExcel`) extracted from the slice-1 / slice-3 orchestrators per [research.md R-1](./research.md#r-1-the-blocking-facades-must-not-touch-isigningsessionstore). Twelve new Domain records / enums / exceptions (per [data-model.md §1](./data-model.md)). One new `WebhookOptions` block on `MisaESignOptions` with five new properties (`Mode`, `Path`, `Secret`, `AllowedIps`, `Session.Ttl`). One new in-memory adapter (`InMemorySigningSessionStore` implementing both `ISigningSessionStore` and `IFinalizeLockOwner`). One new sample-API endpoint file + one IP-allowlist helper. Expected new code: ~3000–3500 LoC including tests and sample-API additions. No new csproj.

**Structure Decision**: Slice 4 is a strict **extension** of the slice-1/2/3 layout — no new csproj, no namespace reshuffles, no copying of HTTP plumbing. The four new consumer surfaces (`BeginSign{Pdf,Xml,Word,Excel}Async` on `IMisaESignClient`) plus the new `HandleWebhookAsync` method are wired through their own thin orchestrator use cases (`BeginSignPdf` / `BeginSignXml` / `BeginSignWord` / `BeginSignExcel` for initiation; `WebhookHandler` for envelope reconciliation + finalize). The four initiation orchestrators reuse 100% of slice 1's `EnsureAccessToken → ListActiveCertificates → ICertificateSelector → format-specific Hash{Format}Document → SubmitSignHash` plumbing via internal `BeginSign{Format}Core` helpers extracted from the existing slice-1 / slice-3 orchestrators (T022–T025); the `WebhookHandler` reuses 100% of slice 3's per-format `AttachSignature{Format}` plumbing. The `SignPdf` / `SignXml` / `SignWord` / `SignExcel` blocking orchestrators are touched only by the internal helper extraction; their behavior, wire shapes, error mapping, and 2FA semantics are preserved byte-identically per FR-089 / FR-091 / SC-032. The `ITokenCache` / `ITokenCacheKeySelector` / `ClientHeadersHandler` / `RemoteSigningAuthHandler` / `TransientFailureRetryHandler` / `SingleFlightRefresh` / `ESignErrorMapper` (extended for one new mapping method) / `ESignLogScrubber` (extended for two new JSON-path matchers) are reused verbatim. The three new ports (`ISigningSessionStore`, `IFinalizeLockOwner`, `IWebhookDeliveryHook`) follow the slice-1 port-and-adapter precedent; the default in-memory adapter `InMemorySigningSessionStore` implements both `ISigningSessionStore` and `IFinalizeLockOwner` so single-process deployments get full functionality from one DI registration. The sample API endpoint at `samples/MisaConnect.Samples.Api/Endpoints/EsignWebhookEndpoint.cs` is the reference webhook wiring; production consumers may copy it or write their own against any HTTP / gRPC / message-bus framework. The slice-4 design is documented in [research.md](./research.md) (12 entries R-1 through R-12) and [data-model.md](./data-model.md); the contracts are pinned in [contracts/](./contracts/) (four files: public-surface, wire-envelopes, error-mapping, sample-api); the consumer-facing rollout sequence is described in [quickstart.md](./quickstart.md).
