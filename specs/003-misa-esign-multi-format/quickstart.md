# Quickstart — `MisaConnect.ESign` slice 3 (multi-format document signing)

How a consumer developer integrates the slice-3 XML / Word / Excel signing facades into their existing slice-1 + slice-2 pipeline. The slice-1 PDF facade and the slice-2 2FA flow continue to work unchanged — the new format facades are pure additions.

> **Note**: This file describes the consumer flow once slice 3 is implemented and the `2.0.0-preview.3` package is published. Implementation is tracked in tasks.md (generated by `/speckit-tasks`).

---

## 1. Upgrade

Bump the package reference:

```bash
dotnet add package MisaConnect.ESign --version 2.0.0-preview.3
```

No configuration changes are required. The slice-1 `Misa:ESign` configuration block keeps working unchanged — no new options are introduced (slice 3 explicitly does not extend `MisaESignOptions`). Existing `AddMisaConnectESign(...)` calls continue to register everything you need; slice 3 just makes three new methods available on the same `IMisaESignClient`.

## 2. Sign an XML document

The XML facade has two equivalent overloads — pick the one that matches what you already hold.

### 2.1. Primary overload — `string`

```csharp
using MisaConnect.ESign.Client;
using MisaConnect.ESign.Client.Dtos;

public sealed class XmlSigningWorkflow
{
    private readonly IMisaESignClient _esign;

    public XmlSigningWorkflow(IMisaESignClient esign) => _esign = esign;

    public async Task<byte[]> SignAsync(string xmlContent, CancellationToken ct)
    {
        var request = SignXmlRequest.FromString(
            xml: xmlContent,
            ctx: new XmlSignatureContextDto(
                SignatureName: "MyInvoiceSignature",
                HashAlgorithm: "SHA256",
                SignatureDescription: new SignatureDescriptionDto(
                    SignedBy: "Acme Co.",
                    ShowSignedDate: true,
                    Location: "Hà Nội",
                    Reason: "Hợp đồng dịch vụ",
                    Contact: "ops@acme.test",
                    DisplayText: null)),
            documentName: "invoice-2026-001.xml",
            dataToBeDisplayed: "Acme Co. — Hợp đồng dịch vụ — 2026-05-22");

        var result = await _esign.SignXmlAsync(request, ct);
        return result.SignedXml;   // UTF-8-encoded signed XML bytes
    }
}
```

### 2.2. Secondary overload — `byte[]` (already-UTF-8-encoded XML bytes)

```csharp
public async Task<byte[]> SignAsync(byte[] xmlUtf8Bytes, CancellationToken ct)
{
    var request = SignXmlRequest.FromUtf8Bytes(
        xmlUtf8Bytes: xmlUtf8Bytes,
        ctx: /* same XmlSignatureContextDto as 2.1 */,
        documentName: "invoice-2026-001.xml",
        dataToBeDisplayed: "Acme Co. — Hợp đồng dịch vụ — 2026-05-22");

    var result = await _esign.SignXmlAsync(request, ct);
    return result.SignedXml;
}
```

> The bytes overload assumes UTF-8 (no BOM stripping, no charset sniffing). If your input is anything other than UTF-8, decode it yourself before constructing the request.

### 2.3. What `XmlSignatureContextDto` accepts vs. what it intentionally hides

| Field | Exposed on `XmlSignatureContextDto`? | Why |
|---|---|---|
| `SignatureName` | yes | Required by MISA §4.2 — names the XAdES signature. |
| `HashAlgorithm` | yes | Defaults to `"SHA256"` — the only value MISA currently supports. Kept as a `string` for forward compatibility. |
| `SignatureDescription` (SignedBy, Location, Reason, Contact, DisplayText, ShowSignedDate) | yes | All six fields carry XAdES-meaningful attestation metadata. |
| `PositionX`, `PositionY`, `Width`, `Height`, `Page`, `SignaturePosInfos` | NO | XAdES signatures have no visual representation. The SDK forbids supplying them via the XML facade (compile-time enforcement). |
| `FontSize`, `FontData`, `SignatureImage`, `LogoImage`, `TextColor`, `RenderingMode` | NO | Same reason — no visual surface for XAdES. The SDK sends MISA-documented "no signature visualization" defaults on the wire so the request stays wire-compatible. |

If you need visual signature appearance, use `SignPdfAsync` / `SignWordAsync` / `SignExcelAsync` — those facades take the slice-1 `SignatureInfo` shape and forward visual position fields verbatim.

## 3. Sign a Word (OOXML) document

```csharp
using MisaConnect.ESign.Client.Dtos;

public async Task<byte[]> SignWordAsync(byte[] wordBytes, CancellationToken ct)
{
    var request = new SignWordRequestDto(
        Word: wordBytes,
        DocumentName: "contract-2026-001.docx",
        SignerName: "Acme Co.",
        Location: "Hà Nội",
        Reason: "Hợp đồng dịch vụ",
        Contact: "ops@acme.test",
        LogoImageBase64: "",                    // empty for non-visual; otherwise base64 of a logo image
        DataToBeDisplayed: "Acme Co. — 2026-05-22",
        Page: 1,                                 // optional visual position
        PositionX: 100,
        PositionY: 100,
        Width: 200,
        Height: 80,
        RenderingMode: 1);

    var result = await _esign.SignWordAsync(request, ct);
    return result.SignedWord;   // signed OOXML .docx bytes
}
```

`SignWordRequestDto`'s shape mirrors slice 1's `SignPdfRequestDto` field-for-field, including the optional position / size / rendering fields. The SDK forwards them to MISA verbatim per FR-059; MISA decides whether to honor them for Word.

## 5. Token caching, 2FA, certificate selection — all the slice-1 + slice-2 behavior carries over

You don't need to do anything special to make the new format facades cooperate with token caching or 2FA:

- **Token cache** — one cached token covers all four formats for the same user. The `ITokenCacheKeySelector` default key is `userName + clientId + base-URL host` per slice 1's FR-026; format is NOT part of the key. After your first `SignXxxAsync` call (any format), the next call (any format) within the cached `expiresIn` window reuses the cached token — zero extra `/login-api` calls (SC-016).
- **2FA-enrolled accounts** — exactly the same flow as slice 2. A 2FA challenge can surface from any of the four facades; you handle it with `SignInWithOtpAsync` (explicit pair) or via a registered `IOtpProvider` (transparent flow). The `OtpChallenge` carries `UserName + CorrelationId` only — nothing format-specific — so your provider implementation works for any format facade.
- **Certificate selection** — the same `ICertificateSelector` (default `FirstActiveCertificateSelector`) picks one certificate per call regardless of which format facade you invoked.

## 6. Branching by `DocumentFormat` on a typed exception

Every typed exception surfaced by the four facades carries a `DocumentFormat Format` property:

```csharp
try
{
    var result = await _esign.SignXmlAsync(request, ct);
    // …
}
catch (ESignGeneralException ex) when (ex.Format == DocumentFormat.Xml && ex.RawCode == "InvalidXmlInput")
{
    // MISA rejected our XML input (malformed body, unsupported variant, etc.)
    // Show the consumer a "your XML couldn't be signed — check it for syntax errors" UX.
}
catch (ESignGeneralException ex) when (ex.Format == DocumentFormat.Xml && ex.RawCode == "MissingSignatureId")
{
    // The signed-attachment request to MISA was missing `signatureId` — likely a SDK bug or a
    // MISA-side reshuffle of the hash response. Log + report.
}
```

The full per-format mapping table is in [contracts/error-mapping.md §A.10](./contracts/error-mapping.md#a10-per-format--documentshash-and--documentsattachment).

The `Format` discriminator also appears on every result type (`SignXmlResultDto.Format = DocumentFormat.Xml`, `SignPdfResultDto.Format = DocumentFormat.Pdf`, etc.) so consumers who unify all four signing paths through one helper can branch on `result.Format` to decide which file extension to save with.

## 7. Logging guarantees (per FR-063 / SC-020)

The SDK redacts the following from every captured log line, exception message, telemetry attribute, and metric label by default across all four formats:

- Source document bytes (`FileToSign` on `/documents/hash` requests for any format).
- Signed document bytes (`document` / `documentBytes` on `/documents/hash` and `/documents/attachment` responses for any format).
- `digest`, `documentHash`, `mainDom`, `sh`, `signatureId`, `signature` values from any request or response body of `/documents/hash` and `/documents/attachment`.

The captured-log unit test (`ESignLogScrubberTests.cs`) and the integration assertion in `PerFormatErrorMappingFakeServerTests.cs` enforce zero occurrences of these values across a full three-format signing exchange.

If you set `MisaESignOptions.Errors.IncludeRawErrorMessage = true`, MISA's `devMsg` / `userMsg` appear on **exception messages** (NOT on the captured request/response logs) — useful for development. The redaction rules above continue to apply to log lines regardless of this flag.

## 9. Exception cheat-sheet (slice-3 additions only)

| You catch | Means | Recommended action |
|---|---|---|
| `ESignGeneralException` with `Format = Xml`, `RawCode = "InvalidXmlInput"` | MISA rejected the XML input | Show "XML couldn't be signed — check syntax" UX. |
| `ESignGeneralException` with `Format ∈ {Word, Excel}`, `RawCode = "MissingMainDom"` | The hash response was missing `mainDom` (SDK or MISA bug) | Log + report; the SDK won't proceed to attachment. |
| `ESignGeneralException` with `Format ∈ {Xml, Word, Excel}`, `RawCode = "MissingSignatureId"` | The hash response was missing `signatureId` | Same as above. |
| `ESignGeneralException` with `Format ∈ {Xml, Word, Excel}`, `RawCode = "UnsupportedDocumentVariant"` | MISA rejected because the format variant isn't supported | Show "we can't sign this document variant" UX. |
| `ESignGeneralException` with any `Format`, `RawCode = "IncompleteHashResponse"` | The /documents/hash response was missing a required field for the requested format | SDK bug or MISA-side change; log + report. |
| `ESignGeneralException` with any `Format`, `RawCode = "MissingSignedDocument"` | The /documents/attachment response was missing the requested format's array | SDK bug or MISA-side change; log + report. The SDK does NOT silently return another format's payload. |

All slice-1 and slice-2 typed exceptions continue to apply — they now carry the matching `Format` discriminator (`Format = Pdf` for slice-1 PDF paths; `Format = Xml | Word | Excel` for slice-3 paths; `Format = Unknown` for failures outside any facade call).

## 10. Migration notes

Slice 3 is purely additive. Slice-1 + slice-2 consumers can upgrade to `2.0.0-preview.3` without code changes:
- `SignPdfAsync` keeps working byte-identically (FR-065).
- `SignInWithOtpAsync` / `ResendOtpAsync` keep working unchanged.
- All slice-1 / slice-2 typed exceptions gain a new `Format` property (with `Format = Pdf` on slice-1 paths, `Format = Unknown` on auth-only paths) — existing `catch (AuthenticationFailedException ex)` blocks keep working; consumers who want to branch by format opt in by reading `ex.Format`.

Adopting the three new format facades is opt-in: import a few new namespaces, construct the new request DTOs, call the new methods.
