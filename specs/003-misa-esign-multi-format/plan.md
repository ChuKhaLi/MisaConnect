# Implementation Plan: MISA eSign — Multi-Format Document Signing

**Branch**: `003-misa-esign-multi-format` | **Date**: 2026-05-22 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/003-misa-esign-multi-format/spec.md`

## Summary

Slice 3 of the `MisaConnect.ESign` product family. It extends slice 1's PDF-only signing pipeline to cover the three remaining MISA-supported document formats (XML, Word, Excel) by introducing three new format-specific facade methods on `IMisaESignClient` (`SignXmlAsync` with two overloads, `SignWordAsync`, `SignExcelAsync`). The wire-shaping work is entirely additive: the existing `HashRequestDto`/`AttachmentRequestDto` already carry the four MISA-published per-format arrays (`pdfDocs`, `xmlDocs`, `wordDocs`, `excelDocs`) — slice 3 fills the three previously-`List<object>` arrays with concrete DTOs that mirror the §4.1 / §4.6 / §4.15 shapes verbatim, and the typed `IMisaESignWireClient` boundary grows three new methods (`HashXmlAsync`, `HashWordAsync`, `HashExcelAsync`) plus two new attachment methods (`AttachSignatureToXmlAsync`, `AttachSignatureToWordExcelAsync` — Word and Excel share a shape per MISA §4.6 once the format-specific array is selected). The Application layer gains the `HashXmlDocument` / `HashWordDocument` / `HashExcelDocument` use cases (siblings of slice 1's `HashPdfDocument`) and a slim `XmlSignatureContext` (Domain) that exposes ONLY the XAdES-meaningful fields; the wire mapping fills MISA-documented "no signature visualization" defaults for the visual fields the slim context omits, so the request stays wire-compatible. The `SignPdf` orchestrator is renamed-by-introduction (slice 1's class stays; a new generic `SignDocument<TFormat>`-shaped pair of orchestrators isn't introduced — each format gets its own thin `SignXml` / `SignWord` / `SignExcel` orchestrator that shares 100% of slice 1's `EnsureAccessToken → ListActiveCertificates → ICertificateSelector → IMisaESignWireClient.Hash...Async → SubmitSignHash → PollSignStatus → AttachSignature` plumbing). Every typed exception surfaced by all four facades gains a closed `DocumentFormat` discriminator (`Unknown = 0`, `Pdf = 1`, `Xml = 2`, `Word = 3`, `Excel = 4`) so consumers can branch error handling by `(ErrorType, Format)` without string-matching. Error mapping extends slice 2's hybrid pattern: canonical `errorCode` table first, then substring synthesis on `errorCode + devMsg` for the format-specific synthesized codes (`InvalidXmlInput`, `MissingMainDom`, `MissingSignatureId`, `UnsupportedDocumentVariant`). The slice extends both test suites — unit tests cover per-format DTO shaping, per-format response extraction, the `mainDom`/`signatureId` required-field profile, the format-property contract, and the per-format error-mapping rows; integration tests add one `[SandboxFact]` per non-PDF format plus full coverage of the three new formats against the in-repo `EsignFake` server. Slice 1's PDF path is byte-identically preserved (FR-065); the only slice-1-touching change is the additive `Format` property on existing typed exceptions, which carries the value `DocumentFormat.Pdf` on every existing PDF-path exception path. Public-surface additions are catalogued in [contracts/public-surface.md](./contracts/public-surface.md); slice 3 ships as `2.0.0-preview.3` (additive minor bump on the still-preview line).

## Technical Context

**Language/Version**: C# 12 / .NET 8.0 (unchanged from slices 1 & 2 — `Directory.Build.props` pins `TargetFramework=net8.0`, `Nullable=enable`, `TreatWarningsAsErrors=true`).
**Primary Dependencies**: No new packages. Slice 3 reuses the slice-1/2 `System.Net.Http` typed `HttpClient` + `IHttpClientFactory`, `Microsoft.Extensions.{Configuration,DependencyInjection,Http,Options,Logging.Abstractions}`, and `System.Text.Json` for wire serialization via `ESignJsonOptions.Wire`. The three new request/response DTO shapes per format land in the existing `Infrastructure/ESign/Wire/HashDtos.cs` and `Infrastructure/ESign/Wire/AttachmentDtos.cs` (next to the slice-1 PDF DTOs) — no new wire files needed because the four-array request envelope already exists; slice 3 fills the previously-`List<object>` arrays with concrete per-format DTO classes.
**Storage**: None. Per-format signed bytes flow through memory; nothing is written to disk. The slice-1 `ITokenCache` is reused as-is — format is NOT part of the cache key (FR-066, slice-1 FR-026). One cached token covers PDF + XML + Word + Excel calls for the same user.
**Testing**: xUnit. Slice-3 unit tests land in three new subfolders under `tests/MisaConnect.ESign.UnitTests/` — `Signing/Xml/`, `Signing/Word/`, `Signing/Excel/` — and one new error-mapping file (`Errors/PerFormatErrorMapperTests.cs`). New integration tests land in `tests/MisaConnect.ESign.IntegrationTests/EndToEnd/` for each format's fake-server happy path plus the format-property contract, plus three `[SandboxFact]` tests under `tests/MisaConnect.ESign.IntegrationTests/Sandbox/` (`SignXmlSandboxTests.cs`, `SignWordSandboxTests.cs`, `SignExcelSandboxTests.cs`) gated by the existing `MISACONNECT_ESIGN_SANDBOX_*` env vars. The in-repo `EsignFake/FakeMisaESignServer.cs` gets per-format request inspection + response handlers added to its existing `/documents/hash` and `/documents/attachment` route methods. Unit-suite budget per the constitution: `< 30s` total — slice 3 inherits this and the cumulative unit suite (slices 1+2+3) must continue to honor it (SC-022).
**Target Platform**: NuGet class library consumed by .NET 8 hosts (Web API, console, worker, MAUI). No platform-specific code paths. XML / OOXML payloads are opaque `byte[]` (or `string` for the XML `string` overload — see FR-050) at the SDK boundary; the SDK does not parse, validate, or transform them.
**Project Type**: Layered class-library product family slice 3. No new csproj. The four production projects (`MisaConnect.ESign.{Domain,Application,Infrastructure,Client}`) and two test projects already exist; slice 3 adds files to them.
**Performance Goals**: No throughput target. Per-call latency for the new format paths matches slice-1 PDF latency closely — same polling window dominance (interval ~2s, total timeout ~60s, both configurable on `MisaESignOptions.Polling`), same transport retry budget. Larger-than-PDF base64 payloads (Word/Excel can be megabytes) flow through `MemoryStream`-backed `JsonContent.Create(...)` exactly as slice-1's PDF path does — no streaming optimization in scope.
**Constraints**:
- Constitution-bound: `Domain` zero external deps (the new `DocumentFormat` enum and `XmlSignatureContext` record are Domain-pure; the new `SignedDocument` per-format variant if any is also Domain-pure); `Application` Domain + `Microsoft.Extensions.Logging.Abstractions` only; Infrastructure `internal` except DI/options/port-interfaces; Client public. Slice 3 introduces no new layer-crossing.
- Logs MUST NOT contain raw source-document bytes, signed-document bytes, `digest`, `documentHash`, `mainDom`, `sh`, `signatureId`, or `signature` values from any format's request or response at any log level by default (FR-063). The slice-1 `ESignLogScrubber` gains per-format JSON-path matchers to extend the existing PDF redactions to `$.xmlDocs[*]`, `$.wordDocs[*]`, `$.excelDocs[*]` on both `/documents/hash` and `/documents/attachment`.
- Wire DTOs match MISA's published shape verbatim per Principle IV. New wire DTOs follow MISA §4.1.1 (PDF/Word/Excel hash-request entry: `DocumentId + FileToSign + SignatureInfo`), §4.1.2 (XML hash-request entry: same field set, `FileToSign` carries raw text), §4.6 (`Doc_Attackment` shape — preserving MISA's misspelling verbatim), and §4.15 (per-format hash-response field set: `documentBytes` for PDF/Word/Excel, `document` for XML; `mainDom` for Word/Excel; `signatureId` for XML/Word/Excel).
- Per-format facades inherit slice 1's `ClientHeadersHandler` (x-clientId/x-clientKey injection), `RemoteSigningAuthHandler` (AuthorizationRM injection, 401 refresh-and-retry, single-flight), `TransientFailureRetryHandler` (bounded 5xx/429/timeout retry), and `ICorrelationIdAccessor` (correlation ID on every request + every surfaced error). No new HTTP-layer behavior.
- Correlation IDs are mandatory and structured on every new log entry and every surfaced typed error from the three new facades (FR-064).
**Scale/Scope**: Three new public facade methods on `IMisaESignClient` (`SignXmlAsync` × 2 overloads, `SignWordAsync`, `SignExcelAsync`), one new closed Domain enum (`DocumentFormat`), one new Domain record (`XmlSignatureContext`), one new Domain record per signed-result if needed (else reuse `SignedDocument`), three new request DTOs + three new response DTOs in the existing wire files, two new attachment-request DTOs (XML + shared Word/Excel) + two new attachment-response array shapes, three new format-specific orchestrator use cases (`SignXml`, `SignWord`, `SignExcel`) that share the slice-1 pipeline, three new `Hash...Async` methods on `IMisaESignWireClient` + two new `AttachSignatureTo...Async` methods, format-property additions on every existing typed exception (additive), error-mapping extensions for the synthesized per-format codes, and per-format request DTO mappers. Expected new code: ~2200–2800 LoC including tests and fake-server endpoints. No new csproj.

**Structure Decision**: Slice 3 is a strict **extension** of the slice-1/2 layout — no new csproj, no namespace reshuffles, no copying of HTTP plumbing. The three new MISA-supported formats (XML, Word, Excel) become five new methods on the existing `IMisaESignWireClient` interface (three hash + two attachment — Word and Excel share an attachment shape because MISA §4.6 publishes one `Doc_Attackment` row that covers both, parameterized by which array carries it). The three new consumer surfaces (`SignXmlAsync` + two overloads, `SignWordAsync`, `SignExcelAsync` on `IMisaESignClient`) are each wired through their own thin orchestrator use case (`SignXml`, `SignWord`, `SignExcel`) that reuses 100% of slice 1's `EnsureAccessToken → ListActiveCertificates → ICertificateSelector → SubmitSignHash → PollSignStatus` plumbing — the only format-specific code lives in the `Hash...Document` and `AttachSignatureTo...` use cases. The `SignPdf` orchestrator is touched only to inherit the new `Format` parameter on every typed exception (forwarded as `DocumentFormat.Pdf`); its behavior is preserved byte-identically per FR-065 / SC-021. The `ITokenCache` / `ITokenCacheKeySelector` / `ClientHeadersHandler` / `RemoteSigningAuthHandler` / `TransientFailureRetryHandler` / `SingleFlightRefresh` / `ESignErrorMapper` are reused verbatim. The XML facade's slim signing-context type (`XmlSignatureContext`) is a deliberate type-system decision (not a runtime check) to prevent consumers from passing visual-positioning fields to a format that has no visual positioning — per the 2026-05-21 spec clarification.
