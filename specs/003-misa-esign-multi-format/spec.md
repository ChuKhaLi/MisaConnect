# Feature Specification: MISA eSign — Multi-Format Document Signing

**Feature Branch**: `003-misa-esign-multi-format`
**Created**: 2026-05-21
**Status**: Draft
**Input**: User description: "Extend the document-signing flow from slice 1 to cover non-PDF document types supported by MISA eSign. The slice adds XML, Word, and Excel document support to /external/esrm/service/document/api/v1/documents/hash and /external/esrm/service/document/api/v1/documents/attachment, with their format-specific request shapes (xmlDocs, wordDocs, excelDocs) and signing-position semantics described in §4 (Mô tả đối tượng) of the API doc. The slice composes the appropriate hash request DTO per format, threads the resulting digest through the same /Signing/hash → /Signing/status → /documents/attachment chain built in slice 1, and returns the signed document bytes in the original format. The deliverable extends slice 1's test suites: unit tests using mock fixtures per format covering DTO shape, signing-position metadata, and per-format error mapping; plus end-to-end integration tests against the MISA eSign sandbox (using MISACONNECT_ESIGN_SANDBOX_* credentials per docs/sandbox-setup.md) that sign one fixture document of each format and verify the returned bytes carry an attached signature. Reuses slice 1's auth, token cache, certificate selection, and signing pipeline. Out of scope: client-side hashing fallback (the PHP/NodeJS path called out in the API doc — MisaConnect always uses MISA's hash endpoint), bulk multi-document signing within a single transaction, and document format conversion. Source doc: docs/misa-api-reference/Tài liệu tích hợp API eSign RemoteSigning - V2.md."

## Clarifications

### Session 2026-05-21

- Q: API surface — per-format methods (`SignXmlAsync` / `SignWordAsync` / `SignExcelAsync`) or a single polymorphic `SignDocumentAsync(bytes, format, …)`? → A: Per-format methods. The four formats form a closed surface that maps 1:1 to MISA's published wire shape; method-name dispatch eliminates a "wrong-arm-of-the-union" bug class and matches slice 1's `SignPdfAsync` shape.
- Q: XML signing-context type — shared `SignatureInfo` (visual fields exposed but no-op for XML) or a slim `XmlSignatureContext` without visual fields? → A: Slim `XmlSignatureContext`. The XML facade does NOT expose `PositionX/Y/Width/Height/Page/SignaturePosInfos/FontSize/FontData/SignatureImage/LogoImage/RenderingMode` to the consumer. PDF / Word / Excel keep slice 1's shared `SignatureInfo` shape. The SDK serializes whatever fields MISA's documented XML hash-file shape requires (`SignatureName`, `HashAlgorithm`, `SignatureDescription`) on the wire, supplying SDK-side defaults for any field MISA marks required that the slim context omits.
- Q: XML input type on the `SignXmlAsync` facade — `byte[]`, `string`, or both? → A: Both, via overloads. Primary overload is `SignXmlAsync(string xml, XmlSignatureContext, …)` (matches MISA's "text content" semantics for `FileToSign` per §4.1.2 and the consumer's natural shape). Secondary overload is `SignXmlAsync(byte[] xmlUtf8Bytes, XmlSignatureContext, …)` for consumers that already hold encoded bytes; the byte overload assumes UTF-8 (no BOM stripping, no charset sniffing) and consumers with non-UTF-8 input must decode themselves. PDF / Word / Excel facades remain `byte[]`-only.
- Q: `Format` discriminator type on surfaced exceptions / Key Entities — closed enum, sealed class hierarchy, or open struct enum? → A: Closed enum `DocumentFormat { Unknown = 0, Pdf = 1, Xml = 2, Word = 3, Excel = 4 }`. MISA's published surface is fixed at four formats; adding a new one is a binary-breaking semver event by definition. The `Unknown` sentinel (value 0, default) covers pre-format-shaping failures (transport, auth-401, validation before the per-format DTO is built) and replaces the looser `Unknown` / `NotApplicable` wording previously used in FR-062.

## User Scenarios & Testing *(mandatory)*

This feature is slice 3 of the `MisaConnect.ESign` product family. It builds directly on slice 1 (`001-misa-esign-pdf-sign-flow`), which already establishes login, token caching, refresh-on-401, header handling, certificate selection, transport retry, the in-repo fake server, and the full PDF-signing pipeline (`/documents/hash` → `/Signing/hash` → `/Signing/status` → `/documents/attachment`). It is independent of slice 2 (`002-misa-esign-2fa-otp`). The actor in each story is a **consumer developer** integrating the SDK into their .NET service; the end user of that service supplies the source document (XML, Word, or Excel) instead of (or in addition to) a PDF.

### User Story 1 - Sign a non-PDF document end-to-end with a single SDK call (Priority: P1)

A consumer developer's service already uses slice 1's PDF signing facade. The consumer's product now needs to sign **XML, Word, and Excel** documents using the same MISA-issued certificate and the same network plumbing. The consumer invokes a format-specific facade method (e.g. `SignXmlAsync`, `SignWordAsync`, `SignExcelAsync`) passing the source document bytes and any signing context (signing-position metadata, reason, signer name). The SDK composes the correct per-format request shape on `/documents/hash`, threads the returned digest through the existing `/Signing/hash → /Signing/status → /documents/attachment` chain, and returns the signed bytes **in the same format the consumer supplied**.

**Why this priority**: This is the headline value of the slice. Without it, MISA-issued certificates can only sign PDFs through this SDK, even though MISA's API supports four formats. P1 because it unblocks every non-PDF use case in a single shippable change; P2 and P3 are quality refinements on top of P1.

**Independent Test**: Drive against the in-repo fake server (no MISA needed) with fixtures for each non-PDF format. For each, supply a one-page fixture document, invoke the format-specific facade, and verify (a) the SDK POSTs to `/documents/hash` with a body that places the fixture in the correct per-format array (`xmlDocs`, `wordDocs`, or `excelDocs`) and leaves the other format arrays empty/absent per MISA's wire shape; (b) the SDK threads the resulting digest through `/Signing/hash → /Signing/status → /documents/attachment`; (c) the returned bytes are non-empty and match the source format (e.g. a Word call returns bytes that begin with the Word OOXML signature, not PDF). Demonstrable end-to-end against the MISA eSign sandbox by repeating the same exercise once per format and asserting that each returned blob carries an attached digital signature.

**Acceptance Scenarios**:

1. **Given** valid sandbox credentials and a user with an ACTIVE certificate, **When** the consumer invokes the XML-signing facade with a well-formed XML document, **Then** the SDK returns signed XML bytes whose root element (or sibling) carries the embedded XAdES signature produced by MISA, within the configured polling timeout.
2. **Given** the same configuration and an OOXML Word document, **When** the consumer invokes the Word-signing facade, **Then** the SDK returns signed Word bytes that open in Word and report a valid digital signature.
3. **Given** the same configuration and an OOXML Excel workbook, **When** the consumer invokes the Excel-signing facade, **Then** the SDK returns signed Excel bytes that open in Excel and report a valid digital signature.
4. **Given** valid credentials and a sequence of three signing calls — one XML, one Word, one Excel — within the cached token lifetime, **When** the calls execute back-to-back, **Then** the SDK performs exactly one `/login-api` request and zero `/Certificates/by-userId` re-fetches between calls (slice 1's caching is preserved).

### User Story 2 - Return signed bytes in the original format without consumer-side dispatch (Priority: P2)

The consumer's service does not need to inspect MISA's per-format response envelope (`pdfDocs`, `xmlDocs`, `wordDocs`, `excelDocs` arrays on `/documents/attachment`'s response). The SDK selects the correct response array based on which facade method the consumer called, extracts the signed-document payload for that format, and returns it as bytes. The consumer never reads MISA's per-format JSON.

**Why this priority**: Wire-format fidelity (Constitution Principle IV) requires the SDK to send and receive MISA's published shapes verbatim, but the consumer should not have to choose which response array to read on every call. Without this, every consumer reimplements the same dispatch logic. P2 because P1's happy path technically works without it — the consumer could parse MISA's response — but no production team would ship that.

**Independent Test**: For each format, drive the fake server to return a `/documents/attachment` response with the signed bytes in the correct per-format array AND populated noise in the other three arrays. Assert that the facade for that format returns exactly the bytes from the matching array, and that calling the wrong-format facade for the same response surfaces a typed "format mismatch" error rather than returning the wrong document.

**Acceptance Scenarios**:

1. **Given** MISA's `/documents/attachment` response populates `xmlDocs[0]` with the signed document and leaves `pdfDocs`, `wordDocs`, `excelDocs` empty (or absent), **When** the consumer called `SignXmlAsync`, **Then** the SDK returns the `xmlDocs[0]` payload as bytes; the consumer does not parse the envelope.
2. **Given** MISA's response populates `wordDocs[0]` and `excelDocs[0]` simultaneously (unusual but documented as legal — the endpoint accepts all four arrays per call), **When** the consumer called `SignWordAsync`, **Then** the SDK returns the `wordDocs[0]` payload only and ignores the `excelDocs[0]` payload without erroring.
3. **Given** MISA's response is missing the array matching the format the consumer requested (e.g. `SignXmlAsync` was called but `xmlDocs` is empty), **When** the SDK surfaces the failure, **Then** it raises a typed "missing signed document" error carrying the correlation ID — it does not silently fall back to a different format's payload.

### User Story 3 - Format-specific error mapping and signing-position semantics (Priority: P3)

When MISA rejects a `/documents/hash` or `/documents/attachment` request for a format-specific reason — malformed XML, unsupported Word/Excel variant, missing `mainDom` on Excel/Word attachment, missing `signatureId` on non-PDF attachment — the SDK distinguishes the rejection from generic transport failures and from cross-format rejections (e.g. "invalid certificate"). The mapped typed error carries the requested format on a dedicated property so the consumer can branch by `(errorType, format)` without string-matching `devMsg`. Logging continues to omit raw document bytes, signature payloads, and certificate private material as required by slice 1's FR-019.

**Why this priority**: Operationally important — Word and Excel signing failures share an MISA error envelope with PDF signing, and the only differentiator is which per-format array carried the request. Without this, consumers cannot tell from the surfaced exception whether their problem is "PDF signing broken" vs "Word signing broken" vs "certificate problem". P3 because P1 happy path works without it, but production support requires it.

**Independent Test**: Drive the fake server with one rejection fixture per format — malformed body, missing required `mainDom` for Excel, missing required `signatureId` for XML attachment — each emitting the documented `errorCode`. Assert: each surfaced exception carries the requested format on a typed property; each carries MISA's `errorCode` and the correlation ID; the surfaced exception type matches the documented mapping; the captured log output contains no raw document bytes from any format, no signature payload, and no certificate private-key material.

**Acceptance Scenarios**:

1. **Given** the consumer calls `SignExcelAsync` and MISA returns a `/documents/attachment` rejection due to a missing `mainDom` field, **When** the SDK surfaces the failure, **Then** the resulting exception's type indicates "format-specific attachment rejection", its format property reads `Excel`, and it carries MISA's `errorCode` + correlation ID.
2. **Given** the consumer calls `SignXmlAsync` and MISA returns a rejection because the input XML is malformed, **When** the SDK surfaces the failure, **Then** the resulting exception's format property reads `Xml` and the rejection is mapped to the same error category as malformed-PDF rejections in slice 1 (consistent cross-format taxonomy).
3. **Given** any successful or failed call across the three new formats, **When** logs are inspected, **Then** no log line contains source-document bytes, signed-document bytes, the `digest`, `documentHash`, or `signature` values from MISA's responses, certificate private-key material, or end-user PII.

---

### Edge Cases

- **Consumer passes empty/zero-byte bytes** to a format-specific facade → surfaced as a typed validation error before any network call is made; no `/documents/hash` request is issued.
- **Consumer passes bytes whose magic-number doesn't match the called facade** (e.g. PDF bytes into `SignXmlAsync`) → the SDK MUST NOT silently re-route to the matching facade. Slice 3 leaves authoritative format validation to MISA (the SDK is not a document validator); MISA's rejection surfaces with the requested-format property set to the format the consumer asked for, so the consumer can detect the mismatch.
- **Signing-position metadata supplied for XML** → XML signatures (XAdES) have no visual position; the SDK forwards the consumer-supplied `SignatureInfo` block on the wire per MISA's shape (positions included), but documents in the assumptions that MISA ignores visual position fields for XML. No client-side stripping.
- **`mainDom` missing in MISA's `/documents/hash` response for Excel or Word** → SDK surfaces a typed "incomplete hash response" error and does not proceed to `/Signing/hash`; the partial transaction does not pollute the consumer's process state.
- **`signatureId` missing in MISA's `/documents/hash` response for non-PDF formats** → same treatment as missing `mainDom`: typed error, no further pipeline calls.
- **MISA's `/documents/attachment` response populates a different format array than the one the consumer requested** (per US3 acceptance scenario 1) → typed "missing signed document" error per FR-053; the wrong-format payload is not returned.
- **Format-specific MISA rejection carrying a generic `errorCode`** (e.g. `400` with no MISA-canonical mapping) → SDK falls back to the same hybrid mapping pattern as slice 2's FR-039 (canonical-code table first, then substring synthesis on `errorCode + devMsg`) and surfaces a typed error carrying the requested format.
- **Polling, refresh-on-401, transport retry, single-flight refresh** — slice 1's FR-004, FR-011, FR-023, FR-028 apply unchanged. Slice 3 does not introduce new transport semantics; only new request/response shaping.
- **Token cache key identity** — slice 1's `ITokenCacheKeySelector` (FR-026) is unchanged. Format is not part of the cache key — one cached token covers PDF, XML, Word, and Excel calls for the same user.

## Requirements *(mandatory)*

### Functional Requirements

Slice 2's last `FR-NNN` is `FR-045`; this slice picks up at `FR-050` with room to grow.

**Public surface — per-format facade methods**

- **FR-050**: `IMisaESignClient` MUST expose three new format-specific facade entry points alongside slice 1's PDF facade: `SignXmlAsync` (XML), `SignWordAsync` (Word), `SignExcelAsync` (Excel). The Word and Excel facades MUST accept `byte[]` for the source document (matching slice 1's PDF facade) plus a slice-1-shaped `SignatureInfo` signing context. The XML facade MUST be exposed as two overloads — `SignXmlAsync(string xml, XmlSignatureContext, …)` (primary; matches MISA's text-content semantics for `FileToSign` per §4.1.2) and `SignXmlAsync(byte[] xmlUtf8Bytes, XmlSignatureContext, …)` (secondary; assumes UTF-8, no BOM stripping, no charset sniffing). Each facade MUST return the signed payload in the same format the consumer supplied: `byte[]` for Word/Excel and for the `byte[]` XML overload; the XML `string` overload MAY return `byte[]` (uniform across overloads) provided the result is UTF-8-encoded so callers can `Encoding.UTF8.GetString` it without ambiguity. Method names are recorded in the slice's implementation contract; renames are semver events.
- **FR-051**: The format-specific facades MUST NOT require the consumer to choose between slice 1's PDF method and a non-PDF method via flags, format enums, or polymorphic dispatch. The consumer's call site selects format **by method name**. Rationale: avoid a "wrong-arm-of-the-union" bug class (passing Excel bytes to a PDF method); preserve a stable, discoverable API surface that mirrors slice 1's PDF facade method-for-method.

**Per-format request DTO shaping (`/documents/hash`)**

- **FR-052**: For each non-PDF format, System MUST place the input document into the correct per-format array on the `/documents/hash` request body — `xmlDocs` for XML, `wordDocs` for Word, `excelDocs` for Excel — and MUST leave the other three format arrays absent or empty, per the MISA published shape (§3 step "Tạo hash của file" of the API doc). Each entry MUST carry exactly the fields the MISA §4.1 sheets require for that format: PDF/Word/Excel use `DocumentId + FileToSign + SignatureInfo`; XML uses `DocumentId + FileToSign + SignatureInfo` with `FileToSign` carrying the XML content as documented in §4.1.2. Field names and casing MUST match MISA's published shape verbatim (Constitution Principle IV).
- **FR-053**: For each non-PDF format, System MUST extract the format-specific response fields from MISA's `/documents/hash` response per MISA §4.15:
  - **XML** (`xmlDocs[]`): `documentId`, `document`, `signatureId`, `digest`, `sh`.
  - **Excel** (`excelDocs[]`): `documentId`, `documentBytes`, `signatureId`, `digest`, `mainDom`.
  - **Word** (`wordDocs[]`): `documentId`, `documentBytes`, `signatureId`, `digest`, `mainDom`.
  If any required field for the requested format is missing or empty on a successful HTTP response, System MUST surface a typed "incomplete hash response" error and MUST NOT proceed to `/Signing/hash` for that transaction.

**Signing pipeline reuse (`/Signing/hash`, `/Signing/status`)**

- **FR-054**: System MUST submit the format-specific `digest` value (from the per-format response entry isolated in FR-053) to `/Signing/hash` using the same request shape and behavior already implemented in slice 1's `FR-010`. Slice 3 introduces no new fields on the `/Signing/hash` request; the format is invisible at this hop.
- **FR-055**: System MUST poll `/Signing/status/{transactionId}` per slice 1's `FR-011`, treating `SUCCESS / FAILED / CANCELLED` semantics identically across formats. The poll-interval and total-timeout options on `MisaESignOptions` apply unchanged.

**Per-format attachment DTO shaping (`/documents/attachment`)**

- **FR-056**: On `SUCCESS`, System MUST POST to `/documents/attachment` with the input document placed into the correct per-format array — `xmlDocs` for XML, `wordDocs` for Word, `excelDocs` for Excel — using the `Doc_Attackment` (sic — MISA's spelling) shape from MISA §4.6: `signature`, `documentId`, `documentBytes`, `digest`, `mainDom`, `signatureName`, `sh`, `signatureId`, `documentHash`. The `mainDom` field MUST be populated for Excel and Word per MISA §4.6 ("bắt buộc với Excel và Word"); the `signatureId` field MUST be populated for XML, Excel, and Word per MISA §4.6 ("trừ pdf"). Field names and casing MUST match MISA's published shape verbatim.
- **FR-057**: System MUST extract the signed-bytes payload from the matching per-format array on MISA's `/documents/attachment` response — `xmlDocs` for `SignXmlAsync`, `wordDocs` for `SignWordAsync`, `excelDocs` for `SignExcelAsync` — and return it to the consumer. The other three format arrays in the same response MUST be ignored without error.
- **FR-058**: If the array matching the requested format is empty or missing on a successful `/documents/attachment` HTTP response, System MUST surface a typed "missing signed document" error carrying the requested format and the correlation ID. System MUST NOT silently return a payload from a different format's array.

**Signing-position semantics per format**

- **FR-059**: For PDF, Word, and Excel signing operations, the consumer-supplied signing context MUST be slice 1's shared `SignatureInfo` shape (per MISA §4.2). System MUST forward the consumer-supplied `SignatureInfo` block on the `/documents/hash` request verbatim, including the visual-positioning fields (`PositionX`, `PositionY`, `Width`, `Height`, `Page`, `SignaturePosInfos`) and the rendering hints (`FontSize`, `FontData`, `SignatureImage`, `LogoImage`, `RenderingMode`, `SignatureDescription`). The SDK MUST NOT strip or default position fields client-side for these three formats.
- **FR-060**: For XML signing operations, the consumer-supplied signing context MUST be a slim XML-specific type (`XmlSignatureContext`) that exposes ONLY the fields meaningful for an XAdES signature: `SignatureName`, `HashAlgorithm`, and the `SignatureDescription` block (`SignedBy`, `ShowSignedDate`, `Location`, `Reason`, `Contact`, `DisplayText`). The XML facade signature MUST NOT accept `PositionX`, `PositionY`, `Width`, `Height`, `Page`, `SignaturePosInfos`, `FontSize`, `FontData`, `SignatureImage`, `LogoImage`, or `RenderingMode` from the consumer. On the wire, System MUST serialize the MISA-required `SignatureInfo` shape from §4.1.2 / §4.2: fields supplied via `XmlSignatureContext` are forwarded verbatim; visual/positioning fields omitted from the slim context MUST be sent as their MISA-documented "no signature visualization" defaults (e.g. zeroed coordinates, `RenderingMode = 0` meaning "diễn giải only"), so the request remains wire-compatible with MISA's published shape. The SDK is not a document validator and MUST NOT pre-validate the consumer's `XmlSignatureContext` against XAdES semantic rules.

**Error mapping and observability**

- **FR-061**: System MUST extend slice 2's hybrid error-mapping strategy (`FR-039`) to format-specific rejections on `/documents/hash` and `/documents/attachment`. When MISA's Postman collection yields a canonical `errorCode` for a per-format rejection (malformed input, missing required field, unsupported variant, signature failure), the SDK MUST map by that `errorCode` directly. When the collection is silent, the SDK MUST fall back to substring synthesis on `errorCode + devMsg` and produce stable internal codes (e.g. `"InvalidXmlInput"`, `"MissingMainDom"`, `"MissingSignatureId"`, `"UnsupportedDocumentVariant"`). Both layers MUST be published in the slice's error-mapping contract alongside slice 1's and slice 2's tables.
- **FR-062**: Every typed exception surfaced by the three new facades MUST carry a `Format` property of type `DocumentFormat` (a closed enum: `Unknown = 0`, `Pdf = 1`, `Xml = 2`, `Word = 3`, `Excel = 4`) identifying which format the consumer requested. The property MUST be set on every surfaced exception including failures that occur before the per-format DTO is built. For pre-format-shaping failures originating below the format-shaping layer (transport, auth-401, validation) the property MUST carry the value matching the called facade (`Pdf` / `Xml` / `Word` / `Excel`) so the consumer's call site can always branch by `Format`; the `Unknown` sentinel is reserved for failures surfaced outside any specific facade call (e.g. background refresh failures, DI-time validation) where no consumer-facing format was requested. Slice 1's existing PDF-path exceptions MUST be updated to carry `Format = Pdf` for the contract to be uniform across formats — this is a no-behavior-change adjustment to slice 1's surface (FR-065 still holds: the wire behavior and observable failure semantics of the PDF path are unchanged).
- **FR-063**: System MUST NOT log raw source-document bytes, signed-document bytes, `digest`, `documentHash`, `mainDom`, `sh`, `signatureId`, or `signature` values from any format's request or response at any log level by default. This extends slice 1's `FR-019` to the new format-specific fields introduced by §4.6 and §4.15.
- **FR-064**: Every outbound `/documents/hash` and `/documents/attachment` request — across all four formats — MUST carry a correlation ID injected by slice 1's `ICorrelationIdAccessor`. The correlation ID MUST appear on every related log entry and on every surfaced typed error, with no per-format gaps.

**Reuse contracts — no regression**

- **FR-065**: Slice 1's PDF signing path MUST continue to work byte-identically after slice 3 ships. The new per-format facades MUST NOT alter slice 1's PDF request shapes, response handling, or error-mapping behavior. A regression test asserts the existing PDF integration test still passes after slice 3 is merged.
- **FR-066**: Slice 1's contracts on auth (`FR-001`–`FR-005`), token cache identity (`FR-026`, including format NOT being part of the cache key), transport retry (`FR-023`–`FR-025`), thread safety (`FR-027`), single-flight refresh (`FR-028`), certificate selection (`FR-006`–`FR-008`), polling (`FR-011`), and observability (`FR-017`–`FR-019`) MUST apply unchanged to the three new format paths. Slice 3 introduces NO new ports, NO new options, and NO new DI surface beyond the three facade methods on `IMisaESignClient`.
- **FR-067**: Slice 2's 2FA contracts (`FR-030`–`FR-045`) MUST apply unchanged: a 2FA-enrolled account can sign XML, Word, and Excel documents through the same `SignInWithOtpAsync` / `IOtpProvider` pathways slice 2 established. No format-specific 2FA behavior is introduced.

**Test deliverables**

- **FR-068**: The unit test project `tests/MisaConnect.ESign.UnitTests/` MUST extend its coverage to include, **per non-PDF format**: per-format request DTO shaping on `/documents/hash` (correct array, correct field set per §4.1), per-format response DTO parsing on `/documents/hash` (correct field extraction per §4.15), per-format request DTO shaping on `/documents/attachment` (`Doc_Attackment` per §4.6 with `mainDom` for Word/Excel and `signatureId` for XML/Word/Excel), per-format response payload extraction on `/documents/attachment` (correct format-array selection per FR-057), per-format error mapping (FR-061), the missing-required-field error path (FR-053 and FR-058), and the "format property on every surfaced exception" contract (FR-062). The combined unit-test latency MUST stay under 30 seconds total (Constitution invariant preserved).
- **FR-069**: The integration test project `tests/MisaConnect.ESign.IntegrationTests/` MUST add one end-to-end `[SandboxFact]` test per non-PDF format that signs a fixture document of that format against the MISA eSign sandbox using `MISACONNECT_ESIGN_SANDBOX_*` env vars (per `docs/sandbox-setup.md`) and asserts the returned bytes carry an attached digital signature verifiable in the corresponding file format. Each `[SandboxFact]` MUST skip cleanly when sandbox credentials are absent or the sandbox is unreachable, but MUST fail loudly when credentials are explicitly rejected by the sandbox.
- **FR-070**: The in-repo fake server at `tests/MisaConnect.ESign.IntegrationTests/EsignFake/` (introduced in slice 1) MUST be extended to serve per-format `/documents/hash` and `/documents/attachment` responses for the three new formats, so the deterministic offline integration tests can exercise the full three-format pipeline without MISA reachability.

### Key Entities

- **Signed Document (per format)** — the final output of `SignXmlAsync` / `SignWordAsync` / `SignExcelAsync`: signed bytes in the same format the consumer supplied. Distinguished from slice 1's PDF-only signed document by carrying a `Format` discriminator on the surfaced result/exception.
- **Per-Format Hash Request** — the format-specific entry inside `pdfDocs` / `xmlDocs` / `wordDocs` / `excelDocs` on `/documents/hash`. PDF/Word/Excel share the §4.1.1 shape (`DocumentId + FileToSign + SignatureInfo`); XML uses the §4.1.2 shape (same field set, but `FileToSign` carries XML text rather than base64 bytes per MISA's wording).
- **Per-Format Hash Response Entry** — the format-specific record inside `pdfDocs` / `xmlDocs` / `wordDocs` / `excelDocs` on the `/documents/hash` response. Each format publishes a different field set per §4.15; the SDK isolates the right entry per requested format and propagates only the fields needed downstream (`digest` to `/Signing/hash`, then the full record to `/documents/attachment`).
- **Per-Format Attachment Entry** — the `Doc_Attackment` shape from §4.6, carrying `signature + documentId + documentBytes + digest + mainDom + signatureName + sh + signatureId + documentHash`. The required-field profile varies by format: `mainDom` is required for Word and Excel; `signatureId` is required for XML, Word, and Excel; PDF requires neither.
- **Signing Context (per format)** — for PDF / Word / Excel: slice 1's shared `SignatureInfo` block from §4.2, exposing visual-positioning and rendering fields. For XML: a slim `XmlSignatureContext` exposing only the XAdES-meaningful fields (`SignatureName`, `HashAlgorithm`, `SignatureDescription`). The two context shapes are forwarded to MISA per FR-059 / FR-060; XML's wire serialization fills MISA-required `SignatureInfo` defaults for fields the slim context does not surface.
- **`DocumentFormat`** — closed enum `{ Unknown = 0, Pdf = 1, Xml = 2, Word = 3, Excel = 4 }`. Appears on every surfaced exception and result from any facade so consumers can branch error handling and so logging can attribute correlation-ID-keyed lines to a format. Adding a new MISA format is a binary-breaking semver event.

## Success Criteria *(mandatory)*

### Measurable Outcomes

Slice 2's last `SC-NNN` is `SC-014`; this slice picks up at `SC-015`.

- **SC-015**: A consumer with valid sandbox credentials can sign one XML, one Word, and one Excel fixture document end-to-end, each with a single SDK facade call — measured by three `[SandboxFact]` tests that all return signed bytes in the matching format within the configured polling timeout.
- **SC-016**: After the first signing call within a session, the next two format-specific facade calls (for any other two formats) within the cached `expiresIn` window perform zero additional `/login-api` and zero additional `/Certificates/by-userId` requests — verified by request counting against the in-repo fake server.
- **SC-017**: For each format, the SDK sends exactly one populated per-format array on `/documents/hash` (matching the called facade) and zero entries in the other three arrays — verified by a unit test that captures and inspects each outbound request body across all three formats.
- **SC-018**: For each format, the SDK returns the signed-bytes payload from the matching per-format array on `/documents/attachment`'s response and ignores any populated entries in the other three arrays — verified by a unit test that drives the fake server with intentionally noisy multi-array responses.
- **SC-019**: Every typed exception surfaced by all four facades (PDF + the three new ones) carries a `DocumentFormat` property whose value matches the called facade (`Pdf` / `Xml` / `Word` / `Excel`, never `Unknown` for in-facade failures) — verified by unit-test coverage of every documented error path per format, asserting `Format` directly without inspecting any string field. Slice 1's existing PDF unit tests are extended to assert `Format == Pdf` on existing exceptions; that extension is the only slice-1-touching change permitted under FR-065.

## Assumptions

1. **API surface — per-format methods, not polymorphic** (confirmed in Clarifications Session 2026-05-21). `IMisaESignClient` exposes a separate method per format (`SignPdfAsync` from slice 1, plus `SignXmlAsync` / `SignWordAsync` / `SignExcelAsync` introduced here) rather than a single polymorphic `SignDocumentAsync(bytes, format, ...)`. Rationale: matches slice 1's existing shape, avoids a "wrong-arm-of-the-union" bug class, and gives each format a distinct entry point in API docs and IntelliSense.
2. **Single-document-per-call only.** Although MISA's `/documents/hash` and `/documents/attachment` endpoints accept arrays of up to N documents per format per request, each slice 3 facade call signs exactly one document. "Bulk multi-document signing within a single transaction" is explicitly out of scope per the slice prompt. A future slice can layer batching on top of this surface without changing it.
3. **No mixed-format batching.** A single facade call signs a single format. The SDK does not expose a "sign a Word and an Excel in one transaction" affordance — even though MISA's endpoints would technically allow it — because no consumer use case in the slice prompt requires it and the API surface stays simpler.
4. **No client-side document validation.** The SDK is not an XML / OOXML validator. Malformed-input rejections are surfaced from MISA, not synthesized client-side. The only validation the SDK performs is "bytes are non-empty" (the edge case above).
5. **Per-format signing-context types** (confirmed in Clarifications Session 2026-05-21). PDF / Word / Excel facades take slice 1's shared `SignatureInfo` shape with all visual-positioning fields exposed and forwarded verbatim. The XML facade takes a slim `XmlSignatureContext` that does NOT expose visual-positioning or rendering fields. On the wire, the SDK fills MISA-required `SignatureInfo` defaults for the omitted fields so the XML request remains wire-compatible. Rationale: hide no-op fields at the call site instead of relying on docstring-only warnings — the type system tells the consumer what is meaningful for XAdES.
6. **`FileToSign` encoding per format follows MISA's documented shape.** Per §4.1.1, PDF / Word / Excel use base64-encoded bytes for `FileToSign`; the SDK base64-encodes the consumer-supplied `byte[]` automatically. Per §4.1.2, XML uses raw text content for `FileToSign`; the `string` overload of `SignXmlAsync` forwards the input verbatim, and the `byte[]` overload decodes via `Encoding.UTF8` before forwarding (Assumption: input is well-formed UTF-8; the SDK does not BOM-strip or sniff alternative encodings). If MISA's wire format diverges from the doc (per the parent plan's Postman-tie-breaker rule), the implementation reconciles via the Postman collection during `/speckit-plan`.
7. **No new ports, options, or DI types.** Slice 3 reuses every port and configuration value introduced by slice 1 (`ITokenCache`, `ITokenCacheKeySelector`, `ICertificateSelector`, `ICorrelationIdAccessor`, `ISystemClock`, `MisaESignOptions`). The only new public-surface additions are the three facade methods on `IMisaESignClient`.
8. **Token-cache key identity does not depend on format.** Per slice 1's FR-026, the default `ITokenCacheKeySelector` composes the key from `userName + clientId + base-URL host`. Format is NOT part of the cache key — one cached token covers signing operations in all four formats for the same user.
9. **The in-repo fake server is the source of truth for offline tests.** Per-format request/response fixtures live in `tests/MisaConnect.ESign.IntegrationTests/EsignFake/` and are committed alongside the integration tests. Real-MISA sandbox tests skip cleanly when env vars or connectivity are missing.
10. **Out of scope (verbatim from the slice prompt)**: client-side hashing fallback (the PHP/NodeJS path in §3 of the API doc — MisaConnect always uses MISA's hash endpoint), bulk multi-document signing within a single transaction, and document format conversion (e.g. converting a Word document to PDF before signing).
11. **The constitution principles** in [.specify/memory/constitution.md](../../.specify/memory/constitution.md) — especially zero-dep Domain, port-and-adapter extensibility, wire-format fidelity (Constitution Principle IV — including MISA's misspelling of `Doc_Attackment`, which is preserved verbatim per FR-056), and no-secrets/no-PII-in-logs (Constitution Principle VIII) — apply to every requirement above.
