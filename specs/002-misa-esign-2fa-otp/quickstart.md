# Quickstart — `MisaConnect.ESign` slice 2 (two-factor authentication)

How a consumer developer integrates the slice-2 OTP support into their existing slice-1 signing pipeline. Two consumer-surface paths are supported; pick whichever fits your UX:

1. **Explicit pair** (recommended when the consumer prompts an end user for the OTP via a UI affordance and there is an asynchronous gap).
2. **Transparent `IOtpProvider`** (recommended when the consumer's service has a synchronous-enough way to obtain an OTP — e.g. an authenticator-app TOTP integration).

Both routes converge on the same Application-layer use case and the same cached token bundle. You can swap between them at any time.

> **Note**: This file describes the consumer flow once slice 2 is implemented and the `2.0.0-preview.2` package is published. Implementation is tracked in tasks.md (generated by `/speckit-tasks`).

---

## 1. Upgrade

Bump the package reference:

```bash
dotnet add package MisaConnect.ESign --version 2.0.0-preview.2
```

No configuration changes are required for existing slice-1 consumers — the new `MisaESignOptions.Otp` block has sensible defaults. Existing `AddMisaConnectESign(...)` calls keep working unchanged.

## 2. Path A — Explicit pair (catch + supply OTP)

Use this when your service exposes a UI affordance for OTP entry (e.g. a web form, a mobile app screen) and the end user supplies the OTP some time after the signing attempt begins.

```csharp
using MisaConnect.ESign.Client;
using MisaConnect.ESign.Client.Dtos;
using MisaConnect.ESign.Domain.Authentication;
using MisaConnect.ESign.Domain.Errors;

public sealed class SignPdfWorkflow
{
    private readonly IMisaESignClient _esign;

    public SignPdfWorkflow(IMisaESignClient esign) => _esign = esign;

    public async Task<SignPdfResultDto> SignAsync(SignPdfRequestDto request, CancellationToken ct)
    {
        try
        {
            return await _esign.SignPdfAsync(request, ct);
        }
        catch (AuthenticationFailedException ex) when (ex.Requires2FA)
        {
            // Show your UI affordance, collect the OTP and otpType from the end user.
            var (otpCode, otpType, remember) = await PromptEndUserForOtpAsync(ex.Username, ct);

            try
            {
                await _esign.SignInWithOtpAsync(otpCode, otpType, remember, ct);
            }
            catch (InvalidOtpException)        { /* show "wrong code" */ throw; }
            catch (ExpiredOtpException)        { /* show "code expired — please request a new one" */ throw; }
            catch (ExhaustedOtpAttemptsException) { /* show "too many attempts — contact support" */ throw; }

            return await _esign.SignPdfAsync(request, ct);   // resumes against the freshly cached tokens
        }
    }
}
```

### 2.1. Re-delivering an OTP that never arrived

When the end user clicks "resend code":

```csharp
OtpResendResultDto result = await _esign.ResendOtpAsync(language: "en-US", ct: ct);
if (!result.Success)
{
    // Show result.UserMsg to the end user, log result.RawCode + result.CorrelationId for ops.
}
```

`ResendOtpAsync` does NOT throw on documented MISA failures — branch on `result.Success`. Transport failures (5xx, 429 exhausted) DO throw `ESignTransportException`.

### 2.2. What `remember` does

`remember: true` is a pure pass-through hint to MISA. The SDK does NOT persist a "remembered device" identifier client-side (per the 2026-05-19 spec clarification). Your service's next signing attempt after a process restart will surface a fresh 2FA challenge if MISA still wants one.

## 3. Path B — Transparent `IOtpProvider`

Use this when your service has a synchronous way to produce an OTP at signing time — for example, a TOTP authenticator integration, a Vault-backed test OTP, or a sandbox account with a fixed OTP for CI.

### 3.1. Implement the provider

```csharp
using MisaConnect.ESign.Application.Abstractions;
using MisaConnect.ESign.Domain.Authentication;

public sealed class MyAuthenticatorOtpProvider : IOtpProvider
{
    private readonly IMyTotpGenerator _totp;

    public MyAuthenticatorOtpProvider(IMyTotpGenerator totp) => _totp = totp;

    public Task<OtpSubmission> ProvideAsync(OtpChallenge challenge, CancellationToken ct)
    {
        var code = _totp.CurrentCode(challenge.UserName);
        return Task.FromResult(new OtpSubmission(
            Code:     code,
            OtpType:  OtpDeliveryChannel.Authenticator,
            Remember: false));
    }

    public Task<OtpResendResult> RequestResendAsync(OtpChallenge challenge, string? language, CancellationToken ct)
        => throw new NotSupportedException("Authenticator-app OTPs cannot be 'resent' — they regenerate every interval.");
}
```

### 3.2. Register the provider before `AddMisaConnectESign(...)`

```csharp
builder.Services.AddSingleton<IMyTotpGenerator, MyTotpGenerator>();
builder.Services.AddSingleton<IOtpProvider, MyAuthenticatorOtpProvider>();   // BEFORE AddMisaConnectESign
builder.Services.AddMisaConnectESign(builder.Configuration);
```

### 3.3. Sign without consumer-visible 2FA bookkeeping

```csharp
var result = await _esign.SignPdfAsync(request, ct);   // 2FA happens internally on the catch + ExchangeOtp + retry path
```

If `MyAuthenticatorOtpProvider.ProvideAsync` returns a wrong OTP, `SignPdfAsync` throws the typed rejection (`InvalidOtpException` etc.) — the SDK does NOT auto-retry inside the same call (per [research.md R-10](./research.md#r-10-behavior-when-iotpprovider-returns-a-wrong-otp--bounded-retry)). The consumer's next `SignPdfAsync` call invokes the provider again.

`appsettings.json`:

```json
{
  "Misa": {
    "ESign": {
      "Environment": "Sandbox",
      "BaseUrl": "https://<sandbox-host>/",
      "ClientId": "<your-clientId>",
      "ClientKey": "<your-clientKey>",
      "UserName": "<your-misa-user>",
      "Password": "<your-misa-password>",
      "Polling":        { "Interval": "00:00:02", "TotalTimeout": "00:01:00" },
      "TransportRetry": { "MaxAttempts": 3, "BaseDelay": "00:00:00.200", "MaxDelay": "00:00:02" },
      "Errors":         { "IncludeRawErrorMessage": false },
      "Otp":            { "DefaultResendLanguage": "en-US" }
    }
  }
}
```

Only `Otp` is new. Existing bindings keep working.

## 5. Logging guarantees

The SDK redacts the OTP `code` from every log line, exception message, telemetry attribute, and metric label per FR-044 / SC-012. You don't need to scrub anything yourself. The captured-log unit test covers:

- The `code` value supplied to `SignInWithOtpAsync` never appears in any captured log.
- The `password` field from `MisaESignOptions` is never propagated past the auth layer.
- A future "remembered device" identifier (if MISA ever adds one) would be redacted automatically by the JSON-path matcher (`$..device*`).

If you set `MisaESignOptions.Errors.IncludeRawErrorMessage = true`, MISA's `devMsg` / `userMsg` appear on **exception messages** (not on the OTP-redacted request logs) — useful for development, NOT recommended for production logs.

## 6. Sandbox testing

Set these env vars in addition to the slice-1 set:

| Env var | Required? | Value |
|---|---|---|
| `MISACONNECT_ESIGN_SANDBOX_OTP_PROVIDER` | Required for `TwoFactorAuthSandboxTests` | Either an absolute path to a console binary that prints an OTP on stdout, or a literal OTP value for fixed-OTP sandbox accounts. |
| `MISACONNECT_ESIGN_SANDBOX_USER_2FA_ENABLED` | Optional | If `"true"`, the test runs. If unset or `"false"`, the test logs a skip reason. |

When the sandbox account is not 2FA-enrolled, the test skips cleanly (`SC-014`); when credentials are present but MISA rejects them, it fails loudly.

For offline / CI work without sandbox access, the integration tests under `tests/MisaConnect.ESign.IntegrationTests/EndToEnd/*FakeServerTests.cs` exercise the same paths against the in-repo `EsignFake` server — no env vars required.

## 7. Exception cheat-sheet

| You catch | Means | Recommended action |
|---|---|---|
| `AuthenticationFailedException` with `Requires2FA = true` | MISA wants an OTP | Show OTP entry UI, call `SignInWithOtpAsync` (or register an `IOtpProvider`). |
| `InvalidOtpException` | Wrong code | "Wrong code — try again." Don't auto-retry. |
| `ExpiredOtpException` | Stale code | "Code expired — request a new one." Offer the resend affordance. |
| `ExhaustedOtpAttemptsException` | Too many wrong attempts | "Too many attempts — contact support." Backoff before any retry. |
| `OtpRejectedException` | Unenumerated rejection | Log `RawCode`, `Detail`, `CorrelationId`. Treat as "OTP did not work — try again later". |
| `AuthenticationFailedException` (not `Requires2FA`) on `SignInWithOtpAsync` | MISA re-issued the 122 challenge from `/two-factor-auth` itself | Restart the workflow: call `SignPdfAsync` again to get a fresh challenge. |
| `ESignTransportException` | Transport-retry budget exhausted | Same as slice-1 — back off and retry later. |

`SignPdfAsync` continues to throw all the slice-1 typed exceptions (`NoActiveCertificateException`, `SignRejectedException`, `SignTerminalStateException`, `SignTimeoutException`, etc.) — they're unchanged by slice 2.

---

## 8. Migration notes

Slice 2 is purely additive. Slice-1 consumers can upgrade to `2.0.0-preview.2` without code changes — `SignPdfAsync` keeps working, and 2FA-enrolled accounts now reach a typed exception instead of failing opaquely. Adopting the new methods is opt-in.
